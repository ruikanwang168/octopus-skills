# 测试用例设计

## 任务边界

只处理一项任务：从目标设计和现有实现中提取可测试行为，生成覆盖新增功能及受影响旧功能的结构化测试用例。

可以为了取证启动本地原型、前端和后端并进行探索性操作，但不要执行正式测试计划、修改产品源码、生成自动化测试代码或连接生产系统。用户只要求评审已有用例、排查缺陷或编写测试报告时，不要使用本 Skill。

## 输入角色与证据关系

除非用户指定其他路径，将当前工作目录视为物料根目录。使用 `rg --files` 发现文件，忽略 `.git/`、`node_modules/`、`dist/`、`build/`、`coverage/`、缓存目录和已生成的测试用例文件。

把四类物料分成三个视角，不要混为同一种事实：

- PRD：定义业务范围，以及明确标识的新增、变更、删除/下线、验收标准和业务规则。
- 可运行原型：定义产品希望呈现的页面、流程、交互、文案和状态，是目标设计的运行时证据。
- 现有前端与后端：定义当前系统基线、历史行为和隐含依赖。前端用于追踪路由、事件、校验和接口调用；后端用于追踪鉴权、业务规则、状态、持久化、幂等、并发和集成。

PRD 明确业务规则决定业务预期，原型决定目标交互细节，现有代码只证明当前实现和回归背景。发现 PRD、原型和代码冲突时不要自行选边，记录冲突、影响和待确认项；代码缺少 PRD 新功能不自动判定为缺陷。

## 深度检索与运行要求

盘点物料后，先读取 `references/deep-retrieval.md`，按其中的运行优先、调用链追踪和停止条件执行；建立操作清单后再读取 `references/coverage-checklist.md`。

必须优先尝试：

- 识别原型和现有系统的启动命令、包管理器、锁文件、环境变量、端口和依赖服务。
- 使用已有依赖启动原型；依赖缺失时，只执行物料中已有的、不会改写源码或锁文件的安装/启动步骤。需要密钥、外部生产服务或破坏性数据操作时停止并记录阻塞。
- 通过端口/HTTP 响应、进程日志和浏览器页面确认启动成功，不能只看到命令返回就认为已运行。
- 静态枚举路由和菜单后，用浏览器逐页访问可达页面，实际触发具有独立结果的操作，记录成功、失败、空态、加载态、异常态、权限态和跳转结果。
- 如果现有前后端有安全的本地启动方式，也要尝试运行以确认基线；无法运行时仍需完成代码调用链检索，并明确哪些结论未经运行验证。

只能使用用户提供或物料明确记录的账号和测试数据，不猜密码、不暴力尝试。检测到生产地址或真实数据时，不执行新增、删除、审批、支付等有副作用操作。

## 工作流程

1. 盘点物料：列出 PRD、原型、前端、后端的路径、启动方式、运行结果和缺失项。
2. 提取变更锚点：从 PRD 提取需求编号、模块、角色、页面、字段、接口、状态、术语和“新增/变更/删除”标记。
3. 建立现状基线：围绕变更锚点检索现有前端路由/组件/事件/API 调用，以及后端路由/校验/服务/模型/权限/消息/任务；追到共享依赖和调用方。
4. 运行并遍历目标原型：按页面、角色和状态记录入口、操作、输入、结果和未访问路径；将运行时证据与源码实现对照。
5. 建立变更影响矩阵：将目标划分为 `新增`, `变更`, `受影响回归`, `删除/下线`, `冲突/待确认`，并记录 PRD、原型、前端、后端和运行时证据。
6. 建立操作清单：为每个具有独立可观察结果的操作分配 `OP-001` 形式的标识，记录角色、入口、前置状态、触发条件、结果、变更类型和证据。
7. 设计用例：每个独立操作至少一条正向用例；对明确规则和高风险影响补充异常、边界、权限、状态、数据一致性、接口和回归用例。
8. 检查覆盖：确认每个 PRD 变更点、每个原型独立操作、每条关键调用链和每个受影响旧功能都有用例或明确未覆盖原因。
9. 输出文件：先生成固定字段 JSON，再运行内置脚本写出 XLSX；用户明确要求 CSV 时才输出 CSV。

## 用例拆分规则

将“具有独立预期的操作”作为最小覆盖单位，而不是把每次点击都拆成用例。满足以下条件时，单独建立用例：

- 操作、规则或状态变化存在独立且可观察的界面、接口或数据结果。
- 失败时能够形成目标明确、可单独定位的缺陷。
- 相同操作在不同角色、前置状态或输入规则下产生不同结果。

页面跳转、聚焦输入框、输入内容、打开普通弹窗和点击保存通常是一个业务目标的执行步骤；当它们自身存在权限、校验、二次确认、状态变化或异常反馈时，再拆成独立用例。新增功能必须覆盖新增操作；未改动但被共享组件、接口、权限、状态或数据模型影响的旧操作必须补回归用例。

例如，“打开新增页 → 填写表单 → 点击保存”是一条“新增成功”用例；必填校验、长度上限、重复数据、无权限保存和重复提交分别建立独立用例。

## 字段与分类

严格使用以下字段和顺序：`所属产品`, `所属模块`, `相关研发需求`, `用例名称`, `前置条件`, `关键词`, `优先级`, `用例类型`, `适用阶段`, `用例状态`, `步骤`, `预期`。

- `相关研发需求`：填写 PRD 编号或章节；只有代码提供依据时填写 `实现依据: 文件路径:行号`。
- `关键词`：至少包含操作标识 `OP-xxx`，并补充 `新增`、`变更`、`回归影响`、角色、流程或风险标签。
- `优先级`：`P0` 用于核心冒烟路径或失败后造成重大且不可逆影响的场景；`P1` 用于主要业务与高风险异常；`P2` 用于低频、低影响和表现层场景。
- `用例类型`：从 `功能`, `异常`, `边界`, `权限`, `接口`, `兼容`, `性能`, `安全`, `UI` 中选择一个主要类型。
- `适用阶段`：从 `系统测试`, `回归测试`, `集成测试`, `验收测试` 中选择；默认 `系统测试`。
- `用例状态`：新生成用例填写 `待评审`。
- `步骤`：使用编号写成可执行动作，写清页面或接口、控件、角色和测试数据。
- `预期`：写成可观察结果；存在多个检查点时使用编号，并与步骤对应。禁止只写“正常”“成功”或“符合预期”。

所有字段必须有值。无前置条件时填写 `无`；无法确认时填写 `待确认: ...`，不要猜测。

## 输出与验收

默认交付：

1. 一个 XLSX 测试用例文件；不要同时输出冗长的 Markdown 用例表。
2. 一段深度检索摘要，列出运行过的服务和 URL、实际访问页面、采用的物料、变更矩阵统计、独立操作总数、已覆盖操作数、回归用例数、未覆盖项和待确认项。

输出前必须满足：

- 每个 `OP-xxx` 至少关联一条正向用例，未覆盖项必须说明原因。
- 每个 PRD 新增/变更点至少关联一条用例；共享依赖影响到的旧功能至少有一条回归用例或明确说明不受影响。
- 每条用例只包含一个独立测试目标，但可以包含完成该目标所需的多个操作步骤。
- 每条用例能追溯到 PRD、原型页面/运行记录、前端代码或后端代码。
- 不把代码现状直接当作正确需求；代码与 PRD/原型冲突时单独报告。
- 不从通用检查清单编造产品行为；没有证据的场景只列为风险建议或待确认项。
- 摘要明确区分“已运行验证”“静态代码证据”和“尚未验证”，不能把静态推断写成运行结果。

## 输出脚本

将 `<skill-root>` 替换为当前 `SKILL.md` 所在目录后执行，不要照抄占位符：

```bash
python3 "<skill-root>/scripts/write_test_cases.py" 用例.json --output 测试用例.xlsx
```

输入 JSON 可以是用例对象列表，也可以是包含 `cases` 数组的对象。脚本校验固定字段和分类值，避免单元格内容被解释成电子表格公式，并拒绝覆盖已有文件；用户明确允许覆盖时添加 `--force`。缺少 XLSX 依赖时自动降级为同名 CSV。
