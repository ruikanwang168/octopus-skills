# 深度检索与运行优先流程

本文件用于指导四类物料的深度取证。目标不是读取最多文件，而是让每个变更点、独立操作和回归影响形成可复核的证据链。

## 1. 启动前盘点

先查看目录树、README、package manifest、锁文件、Docker/Compose、环境变量示例和启动脚本，记录：

- 原型、现有前端、后端分别位于哪个目录。
- 包管理器和实际启动命令。
- 需要启动的依赖服务、端口、健康检查地址和演示账号来源。
- 是否指向真实服务、真实数据库或生产域名。
- 启动前缺少的依赖、密钥、数据和环境变量。

不要根据猜测拼接启动命令。优先使用 README、脚本和 manifest 中已有命令。

## 2. 运行原型

按以下顺序验证，而不是只运行一次命令：

1. 使用现有依赖启动原型；如果依赖缺失，只执行锁文件约束的安装方式，不改写源码或锁文件。
2. 检查进程日志、端口监听、HTTP 状态和页面标题/根节点，确认服务真的可用。
3. 静态枚举路由、菜单和入口，再用浏览器访问每个可达页面。
4. 对每个页面记录可触发操作、角色要求、前置状态、输入控件、反馈提示、网络请求、跳转、空态、加载态和异常态。
5. 只在本地或明确的测试环境执行新增、编辑、删除、审批等有副作用操作；生产地址或真实数据只做只读观察。
6. 账号只能使用用户提供或物料明确记录的账号，不能猜测或暴力尝试。

对每条静态路由标记 `已访问`、`需要账号`、`运行阻塞` 或 `不存在`，不能把未访问页面当成没有功能。

如果原型无法运行，记录具体命令、错误、缺失依赖和阻塞位置，然后继续完成静态检索；摘要中明确哪些结论未经运行验证。

## 3. 建立现有系统基线

围绕 PRD 变更锚点和原型操作，在现有代码中做两轮检索：

- 广度检索：路由、菜单、页面、组件、API 客户端、后端路由/controller、DTO/schema、service、model/repository、权限、状态枚举、配置、消息和定时任务。
- 深度追踪：从页面事件追到 API 请求，从 API 追到后端路由、参数校验、鉴权、service、事务、持久化、消息/第三方调用，再反向搜索共享调用方和受影响页面。

搜索时同时使用 PRD 术语、页面文案、路由片段、接口路径、字段名、状态值、错误码和领域实体名，不能只搜索需求标题。

## 4. 现状—目标—变更映射

为每个目标建立一行映射：

| 视角 | 要回答的问题 |
| --- | --- |
| PRD | 这是新增、变更、删除/下线还是背景要求？验收标准是什么？ |
| 原型 | 目标页面、入口、操作、反馈和状态是什么？运行时是否验证？ |
| 前端 | 哪个路由、组件、事件、校验、状态和 API 调用承载它？ |
| 后端 | 哪个接口、权限、业务规则、状态、数据和集成承载它？ |
| 影响 | 哪些旧页面、共享组件、接口、服务、模型、权限或任务需要回归？ |

分类规则：

- `新增`：PRD 明确新增且原型有目标交互；代码尚不存在也要生成目标用例。
- `变更`：现有能力的流程、字段、权限、状态、提示或接口契约改变。
- `受影响回归`：没有直接改动，但复用了变更后的共享依赖。
- `删除/下线`：目标设计移除现有入口或能力，同时检查不可见、不可调用和历史数据影响。
- `冲突/待确认`：多个来源无法一致解释，输出问题，不把任何一方伪装成确定事实。

## 5. 深度检索停止条件

达到以下条件后停止扩展，避免无限读取无关文件：

- 每个 PRD 新增/变更点都有目标操作或未覆盖原因。
- 每个原型可达页面和独立操作都有访问/阻塞记录。
- 每个独立操作都追到前端入口和后端边界；纯前端操作要说明无后端调用。
- 每个变更接口、服务、权限、状态、模型和外部依赖的直接调用方已检查。
- 共享依赖产生的旧功能已归类为回归或有证据说明不受影响。
- 所有运行阻塞、来源冲突、缺少账号/数据和静态推断已单独列出。

文件数量不是完成标准；证据链完整才是完成标准。
