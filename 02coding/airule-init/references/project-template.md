# harness/PROJECT.md 生成规则

## 文件职责

`harness/PROJECT.md` 是项目快照与技术基准，必须结合真实项目填写项目概述、核心技术栈、核心架构与目录规约、代码规范与常用命令、硬性规则（必须遵守）五个部分。

生成 `harness/PROJECT.md` 前必须做源码级深度检索。不能只读取 README、包管理文件或配置文件后就开始写。

源码检索必须先读取并遵守 `harness/AI_IGNORE.md` 或按 `incremental-mode.md` 识别的待迁移旧版忽略文件。新旧位置均缺失时，在写入前临时采用 `ai-ignore-template.md` 的默认忽略范围，避免把依赖目录、构建产物、日志、本地环境文件或敏感文件纳入项目事实。

## 源码检索要求

生成或更新 `harness/PROJECT.md` 前，至少完成以下检索：

1. 扫描边界：先读取 `harness/AI_IGNORE.md` 或待迁移的旧版忽略文件，建立忽略列表和允许读取例外；后续检索跳过被忽略路径。
2. 项目结构：使用 `rg --files` 或同等方式列出主要文件，识别源码目录、配置目录、测试目录、脚本目录、构建产物目录。
3. 技术栈证据：读取包管理、构建和运行配置，例如 `package.json`、`pnpm-lock.yaml`、`pom.xml`、`build.gradle`、`pyproject.toml`、`requirements.txt`、`go.mod`、`Cargo.toml`、`Dockerfile`、`docker-compose.yml`。
4. 入口与启动：定位应用入口、路由入口、服务启动类、CLI 入口、主配置文件和环境变量示例。
5. 架构分层：检索控制器、路由、页面、组件、服务、数据访问、模型、状态管理、任务调度、工具函数等目录和命名模式。
6. 数据与外部依赖：检索数据库 schema、迁移脚本、ORM 模型、API 客户端、第三方 SDK、消息队列、缓存、对象存储等集成点。
7. 测试与质量：检索测试目录、测试框架、lint/format/typecheck 脚本、CI 配置和提交检查配置。
8. 代码风格：抽样读取关键模块，不少于 3 类文件；小项目可读完整源码，大项目按模块抽样，确认命名、分层、错误处理和注释风格。

如果项目很大，不要全文读入；先用文件列表和搜索定位关键模块，再抽样读取代表性文件。

## 抽取规则

- 项目概述必须来自真实代码职责，不只复述仓库名。
- 被 `harness/AI_IGNORE.md` 忽略的路径不得作为项目事实来源，除非用户明确要求读取或该任务必须读取；此时需要在摘要中说明原因。
- 技术及版本必须从真实项目文件核实；区分精确版本与声明的版本范围，无法确认时写“版本待确认”。“核心技术栈”只用列表描述技术名称、版本、用途和技术红线，不附配置内容、配置文件路径或来源标注。
- 技术栈以外的关键事实尽量标注来源文件，例如启动命令、测试命令和核心目录职责。核实依据不必全部展示在正文中。
- “核心架构与目录规约”必须使用 `text` 代码块中的目录树展示，以项目根目录为起点，用 `├──`、`└──`、`│` 表达层级，并在核心目录、入口和配置文件旁简注职责及必要的修改约束。只展示实际存在且允许扫描的路径，不照搬标准目录；大项目展开到能说明模块边界的层级即可，不穷举全部文件。
- 如果代码和 README 描述不一致，以代码和配置文件为准，并在 `harness/PROJECT.md` 中标注待确认。
- 对无法确认的信息写“待确认”，不要猜测。
- “硬性规则（必须遵守）”必须把维护者约定翻译成可判定的条件：明确适用范围、检测对象、禁止或必须满足的条件及检查方式。约束来自项目现有规则、检查配置或维护者明确要求；源码中的常见写法只能用于提出候选规则，不能直接升级为强制约束。
- `harness/PROJECT.md` 正文只保留当前项目事实和现行开发规则，不写“旧规则写了什么、已移除什么、这次更新修正了什么”等增量过程说明；这些内容只放在聊天摘要或更新摘要里。

## 将主观约定转换为机械规则

初版应是项目约束的可检查表达，按以下方式生成，不预置任何项目的具体阈值或语言禁令：

1. 提取依据：读取维护者规则及已有 lint、静态分析、覆盖率、工具链和 CI 检查配置，选取适用于当前语言和模块的约束。用户用于说明写法的参考示例只用于理解表达方法，其中的数值、版本、API 和分层限制不构成项目要求；只有存在独立项目依据或维护者明确选定，才可纳入生效规则。
2. 定义对象与范围：把“短、规范、统一、纯、充分”等主观词落实到具体对象。规模约束写明度量对象、行数计算口径和排除范围；调用或依赖约束写明调用方、被调用方、导入路径、符号或语法结构；不得仅写“禁止不规范代码”或“遵循现有约定”。
3. 写清判定条件：需要数值时写明指标、比较符和已确认阈值；版本限制区分精确版本、允许范围、编译目标和运行时要求；覆盖率区分指标类型、统计范围和排除项。不得从参考示例、当前代码平均值或单个兼容性配置推断项目硬性门槛。
4. 给出检查方式：优先使用项目已有且确实能检查该条件的命令；没有自动检查时，写出可重复的检查步骤，明确检查对象和违规条件。符号调用、继承关系、依赖方向等语义规则应通过符号或语法分析判断，不能把简单文本命中直接当成违规结论。不得虚构检查命令，或声称未接入的规则已由 CI 强制执行；本技能不为此安装工具或修改 CI。
5. 处理不确定项：条件缺失时列明具体待确认项，不自行补数值、扩大禁用范围或把候选建议列成必须遵守的规则。已有例外必须明确保留；涉及新增例外时同样标为待确认。
6. 校验表达：对每条生效规则，执行者应能根据同一适用范围和条件判断通过或违规，无需重新解释团队品味。删去只有价值判断、没有检测对象或判定条件的通用禁令。

## 生成规则

- 生成时按 `agents-template.md` 的元信息约定填写头部，替换日期占位值并使用真实负责人或 `unassigned`；更新正文时同步实际更新日期，保留未变更的负责人和状态。
- 每一节都必须有项目特定内容；信息不足时写“待确认”，并列出需要用户确认的具体问题。
- 技术栈只写能从项目文件确认的事实。
- 命令必须来自真实文件，例如 `package.json`、`Makefile`、`pom.xml`、`pyproject.toml`、`README.md`。
- 关键事实无法核实时，改写为“待确认”，不要当成事实写入；技术栈正文不附来源不代表可以省略核实。
- 硬性规则必须以列表给出适用范围、判定条件和检查方式；具体内容来自实际项目约束，不照搬参考示例或通用语言规则。
- 更新模式下，先校验旧内容是否仍符合当前项目文件；不能确认的内容标为待确认，不继续当成事实。
- 更新模式下，保留开发人员对硬性规则的修改。机械化改写不得改变原规则的范围、阈值和例外；需要补充条件时列出待确认项，与新技术栈冲突时列明冲突，不自动改写人工规则的含义。
- 生成完成前，检查 `harness/PROJECT.md` 的事实性结论是否能追溯到实际文件；不能追溯的内容删除或改为待确认。候选规则与已确认约束必须明确区分，不能因标注“初版”就将未经确认的限制写成生效规则。
- 生成完成前，检查 `harness/PROJECT.md` 是否引用了 `harness/AI_IGNORE.md` 中被忽略的路径；如有引用，删除该结论或改为待确认并在聊天摘要中说明。
- 生成完成前，删除正文中的更新过程痕迹，例如“旧规则中的描述已移除”“本次新增”“原来是”等审计说明。
