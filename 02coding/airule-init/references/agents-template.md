# AGENTS.md 生成规则

## 文件职责

`AGENTS.md` 是 Codex 入口和项目主记忆文件，面向代码生成与分析 AI，定义其在当前项目中的角色边界、执行 SOP、文件快速导航、文档状态管理、需求进度跟踪和代码输出规范。Claude Code 通过 `CLAUDE.md` 指针读取此文件。主记忆文件记录进度维护规则，各计划的实时进度保存在对应的 `进度.md` 中。

## 默认模板

除非用户明确要求改名或调整结构，否则 `AGENTS.md` 使用下面结构。

````md
---
last_updated: YYYY-MM-DD
status: active
owner: unassigned
---

# 角色边界与协作规范

本文件面向代码生成与分析 AI，定义你在本项目的执行 SOP（标准作业程序）。

## 零、进入仓库必读

首次进入仓库或开始任何实质性编码前，必须按顺序读取：

1. `harness/PROJECT.md`：了解项目概述、技术栈底线、架构分层、目录规约和代码风格红线。
2. `harness/USER_RULES.md`：了解项目维护者手写的特殊约束、个人偏好和长期规则。该文件由用户维护，除非用户明确点名要求修改，否则禁止自动改写或覆盖。
3. `harness/AI_IGNORE.md`：了解 AI 在扫描、分析、总结和生成规则时必须忽略的文件、目录、glob 和正则匹配。该文件由用户维护，除非用户明确点名要求修改，否则禁止自动改写或覆盖。

开始或继续某个研发计划前，还必须读取对应计划目录的 `需求.md`、`进度.md` 和关联任务记录，确认已完成项、未完成项、阻塞原因和下一步。

## 一、快速导航

按当前目的查找资料，以下路径均相对于项目根目录：

| 你想做什么 | 去哪里看 |
| --- | --- |
| 了解项目技术栈、架构、目录规约和硬性规则 | [harness/PROJECT.md](harness/PROJECT.md) |
| 查看维护者的特殊约束和个人偏好 | [harness/USER_RULES.md](harness/USER_RULES.md) |
| 确认扫描和检索时的忽略范围 | [harness/AI_IGNORE.md](harness/AI_IGNORE.md) |

- 每次在 `harness/` 及其任意子目录中生成文件，都必须同步在本表中登记，每个文件独立一行；需求、进度、各次任务、设计文档、数据库文件及其他文件均包含在内，不限于 Markdown。
- “你想做什么”用具体用途描述；涉及计划或执行批次时带上计划标识、执行编号或模块名，避免不同文件的用途无法区分。“去哪里看”使用指向实际文件的 Markdown 链接，路径相对于项目根目录，不使用占位路径、通配符或目录链接代替文件记录。
- 文件移动或重命名时更新原行路径，删除文件时移除对应行，文件用途变化时更新描述；同一文件不重复登记。每次执行结束前核对本次新增或变动文件与本表一致，不留下失效链接。
- 文档标记为 `deprecated` 时保留导航记录，在用途描述中标明已废弃；已知替代文档时说明替代位置。
- 需要定位计划或设计资料时，先查本表，再按已读取的扫描边界访问对应文件。

## 二、通用原则

1. 语言：所有沟通和文档产出强制使用中文。
2. 行动前确认：如果不清楚当前任务是“开发新功能”还是“修改老功能”，必须先向用户提问，禁止盲目猜测修改。
3. 前置上下文：如果没有读取 `harness/PROJECT.md`、`harness/USER_RULES.md` 和 `harness/AI_IGNORE.md`，不得开始编码。
4. 扫描边界：在检索、总结、分析或生成规则前，必须先读取并遵守 `harness/AI_IGNORE.md`。
5. 规则优先级：`harness/USER_RULES.md` > `harness/AI_IGNORE.md` > `harness/PROJECT.md` > `AGENTS.md` > `CLAUDE.md`。
6. 冲突处理：如果 `harness/USER_RULES.md` 与其他规则冲突，优先遵守 `harness/USER_RULES.md`；如果涉及扫描范围，以 `harness/AI_IGNORE.md` 为准；仍不确定时先向用户确认。

## 三、研发计划与设计文档（harness 目录）

所有路径均相对于项目根目录。项目规则和研发资料统一放在 `harness/`，按以下边界读写：

- `harness/plan/YYYYMMDD-<计划标识>/`（研发计划）：读写。目录名以用户本地时区的计划创建日期开头，后接计划简名或编号，例如 `20261021-登录功能改造`。同日不同计划使用不同后缀，后续执行沿用原计划目录。每个目录保存该计划的 `需求.md`、`进度.md`，以及各次执行的任务 Markdown、数据库变更文件及其他相关文件。
  - 新建计划时先编写 `需求.md`，根据用户提供的需求记录本次任务的背景、目标、范围、约束和验收标准；未明确的信息标为待确认，不编造。每次执行前先读取此文件，需求变更以用户明确提出或确认的内容为依据。
  - `进度.md` 保存整个计划的需求完成进度，按下节规则维护。
  - 每次执行使用独立编号，例如 `001-任务.md`、`001-db.sql`；任务文件记录本次涉及的需求编号、目标、任务清单、状态和结果，阶段完成后及时更新。后续执行使用新编号，不覆盖此前执行记录。
  - 数据库文件仅在涉及数据库变更时创建，格式沿用项目实际约定；涉及表结构或字段变更时，先在当前计划目录记录 Schema 或迁移方案，再生成代码。
  - 其他执行产物归入同一计划目录；已有需求资料按原有权限使用，不擅自改写。
- `harness/design/`（设计文档）：读写。保存需要长期维护的系统、模块和功能设计，计划任务可引用对应文档。
  - 新功能：开发前必须先在此目录生成技术实现方案（含核心逻辑说明）。
  - 老功能修改：绝对红线：对已有功能进行代码修改后，必须同步更新此处对应的 `.md` 设计文档，保持代码与文档一致。

初始化时只创建空目录 `harness/plan/`、`harness/design/`；实际研发时创建计划目录及 `需求.md`、`进度.md`，执行文件按需创建。

## 四、需求完成进度跟踪

1. 新建计划时，为 `需求.md` 中需要交付的需求条目分配稳定编号（如 `R001`），并在 `进度.md` 中逐项建立记录；同一需求在后续执行中沿用原编号。
2. `进度.md` 以表格记录需求编号、需求摘要、当前状态、关联任务文件、验收结果或证据，以及阻塞原因。状态统一使用：未开始、进行中、待验收、已完成、阻塞。
3. 开始执行时将涉及的需求标为进行中；完成开发但尚未通过验证或验收时标为待验收。只有满足对应需求的验收标准且验证通过，才能标为已完成并记录证据；若需求要求用户验收，还须取得用户的验收结果。遇到阻塞时记录原因及所需条件。
4. 每完成一个阶段、验证得到新结果或出现阻塞时，同步更新 `进度.md` 与相关任务文件；每次执行结束或交接前，写清当前执行编号、剩余事项、阻塞项、下一步和更新时间，供后续会话继续执行。
5. 进度汇总按需求条目统计已完成数与需求总数，不用代码修改量或任务勾选数代替需求完成情况。需求范围变化时，根据用户明确提出或确认的内容同步需求文件和进度记录，不自行删减未完成需求。

## 五、代码输出规范

1. 完整性：每次必须输出完整、可运行的代码，严禁使用 `// ...此处省略代码`。
2. 安全性：在执行终端命令，尤其是删除、移动文件前，必须向用户确认风险。

## 六、提交规范

- feat: 新功能
- fix: 修复
- refactor: 重构
- docs: 文档
- test: 测试

## 七、文档元信息与有效性

以后生成的每个 Markdown 文档都必须在文件最开头添加 YAML 元信息，正文位于结束分隔线之后。适用于 `AGENTS.md`、`CLAUDE.md` 和 `harness/` 下的规则、需求、进度、任务、设计等 Markdown 文档；SQL 等代码文件保留其原有文件格式。

```yaml
---
last_updated: YYYY-MM-DD
status: active          # active | deprecated | draft
owner: unassigned
---
```

- `last_updated`：填写用户本地时区的实际创建或内容更新日期，格式为 `YYYY-MM-DD`；不复制示例日期，不因扫描、读取或原样移动文件而刷新日期。
- `status`：`active` 表示当前有效，`deprecated` 表示已明确废弃，`draft` 表示尚未定稿。按文档当前状态填写，不因日期较早擅自修改状态。
- `owner`：填写维护者明确指定的负责人；未指定时写 `unassigned`。使用 `@账号` 时写成带引号的 YAML 字符串，如 `owner: "@账号"`，不把示例姓名当作实际负责人。
- 扫描或引用文档前，先遵守 `harness/AI_IGNORE.md`，再读取允许访问文档的元信息。默认跳过 `deprecated` 文档，不将其作为现行项目事实或规则；用户明确要求查看历史资料时可以读取并标明已废弃。`draft` 可用于当前草拟或评审任务，不能直接作为已确定的规则或结论。
- 没有明确的有效期规则时，日期只能用于识别需要复核的文档，不得仅因日期较早就忽略 `active` 文档。元信息缺失或格式错误时列为待检查，不默认判为废弃。主入口、必读规则和用户点名文件仍须定位并确认状态，不能以此绕过读取要求；必读文件已废弃但没有替代文件时报告上下文缺口。
- 修改文档内容时同步维护元信息；已有负责人和状态没有变更依据时保留原值。未获授权修改的 `harness/USER_RULES.md`、`harness/AI_IGNORE.md` 及原样迁移文件，不因补头部或刷新日期而被改写。这些字段用于指导 AI 选择上下文，不代表编辑器已建立定时扫描或文件访问屏蔽。
````

## 生成规则

- 可以在不改变核心含义的前提下补充项目特有协作规则。
- 如果目标项目不是代码仓库，或不存在开发任务语境，要先确认是否仍需要 `harness/` 研发资料结构。
- 更新模式下，保留用户已经补充的有效项目特定规则，不把模板硬覆盖上去。
- 如果 `AGENTS.md` 中已有与 `harness/PROJECT.md` 重复的技术栈或目录说明，优先把技术细节迁移到 `harness/PROJECT.md`，`AGENTS.md` 保留职责边界和流程规则。
- `AGENTS.md` 必须包含“进入仓库必读”章节，直接要求读取 `harness/PROJECT.md`、`harness/USER_RULES.md` 和 `harness/AI_IGNORE.md`。
- `AGENTS.md` 必须在必读说明后包含“快速导航”表格，表头为“你想做什么”“去哪里看”。初始化登记三个配套规则文件；项目已有 `harness/` 资料时，按扫描边界核对实际文件并补齐导航，不凭空加入示例计划或不存在的文件。
- 导航覆盖本次在 `harness/` 下创建或迁移的每个文件，不限扩展名；每个文件独立一行，填写具体用途及实际链接，移动、重命名或删除时同步维护。不得为补全用途而读取忽略文件，无法确认的用途标为待确认。
- `AGENTS.md` 必须包含“需求完成进度跟踪”章节，要求执行计划前读取 `需求.md`、`进度.md` 和关联任务记录，并明确状态、完成判定依据及更新时机。
- `AGENTS.md` 必须包含“提交规范”章节，列出上述五种提交类型及其含义。
- `AGENTS.md` 必须包含“文档元信息与有效性”章节，规定所有后续生成的 Markdown 文档使用上述头部，并写明状态过滤、日期判定边界和用户维护文件的保护规则。
- 模板头部中的 `YYYY-MM-DD` 在实际生成时替换为用户本地时区的当天日期；本模板及其他规则文件模板遵守相同元信息约定。
- 生成的路径必须相对于项目根目录，不能把 `harness/` 解释为文件系统根目录；忽略文件中的匹配模式仍以项目根目录为基准。
- `AGENTS.md` 必须写明 `harness/USER_RULES.md` 不属于自动增量更新范围。
- `AGENTS.md` 必须写明 `harness/AI_IGNORE.md` 不属于自动增量更新范围，且 AI 扫描前必须读取并遵守。
- `AGENTS.md` 必须写明规则优先级：`harness/USER_RULES.md` > `harness/AI_IGNORE.md` > `harness/PROJECT.md` > `AGENTS.md` > `CLAUDE.md`。
