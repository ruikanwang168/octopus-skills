## 业务模块的判定

业务模块必须形成可独立验收的业务闭环，通常包含参与者、业务动作、核心对象、状态变化和可观察结果。页面、Controller、Service、数据库表和公共组件都不是独立业务模块。

满足下列条件时倾向拆成不同模块：

- 拥有不同的核心业务对象或生命周期；
- 可以独立启用、验收或交付；
- 存在独立的状态流转、权限边界或业务规则；
- 下游模块只消费其稳定输出，不需要参与其内部过程。

满足下列条件时倾向合并：

- 只是同一对象的列表、详情、新增和编辑页面；
- 只是同一业务动作在前端、后端和数据库的不同技术层；
- 单独拆出后没有可验收业务结果；
- 必须在同一事务或状态流转中同时完成。

## 模块拆分方法

从 PRD、原型和代码中提取：

1. 参与者：谁发起、处理或查看；
2. 业务动作：创建、提交、审批、分派、核销、结算、查询等；
3. 核心对象：动作围绕什么数据对象发生；
4. 状态变化：动作前后状态如何变化；
5. 业务输出：完成后为后续模块提供什么稳定结果。

把共享同一业务结果和数据所有权的动作归入一个模块。再按“基础主数据 → 核心业务创建 → 业务处理 → 查询统计”的依赖顺序排列；只有物料确实包含这些能力时才加入，不补造通用模块。

模块确认稿必须回答：

- 本模块最终让谁完成什么；
- 管理哪些对象和状态；
- 包含与不包含什么；
- 从前序取得什么，本模块交付什么；
- 为什么必须排在当前位置。

## AI 研发任务包

最终前端、后端或单体计划以任务包为最小单位。每个任务包固定包含：

| 字段 | 要求 |
|---|---|
| 任务编号 | 使用 `FE-M01-T01`、`BE-M01-T01`、`APP-M01-T01` 等稳定编号 |
| 变更类型 | 新增 / 修改 / 复用 |
| 目标目录 | 写可直接定位的完整目录；多个目录逐项列出 |
| 主要结果 | 只描述一个主要可交付结果 |
| 实施要点 | 写 2 至 5 个业务或工程要点，不写函数级步骤 |
| 输入/前置 | 写依赖的接口契约、数据对象或前序任务编号 |
| 输出 | 写页面、接口、状态、表结构或联调能力 |
| 验收 | 写能够检查成功或失败的条件 |

任务包过大时按业务结果拆分，不按 Controller、Service、Mapper 机械拆分。任务包过小时合并同一目录、同一结果和同一验收条件下的工作。

## 前端任务包

前端计划至少覆盖实际涉及的这些方面：

- 页面、路由和入口；
- 表单字段、校验和交互状态；
- 列表、详情、操作反馈和异常展示；
- API 客户端、类型、状态管理和联调；
- 权限控制、埋点或测试，仅在需求或现有代码需要时加入。

不要把“写页面”“接接口”作为没有对象和结果的笼统任务。应写明针对哪个业务对象、实现哪些操作、依赖哪个接口、产生什么用户可见结果。

## 后端任务包

后端计划至少覆盖实际涉及的这些方面：

- 接口入口、请求/响应对象和已有规范复用；
- 业务校验、状态流转、计算规则和事务边界；
- 数据模型、查询、写入、索引和迁移；
- 与现有模块或外部系统的集成；
- 并发、幂等、权限和测试，仅在业务或现有代码需要时加入。

不要把 Controller、Service、Repository 各拆成一个任务。围绕一个业务结果组合相关技术层，并在目标目录中分别列出改动位置。

## 粒度检查

合格任务包应满足：

- 另一个 AI 只读当前模块、接口契约和任务包即可开始工作，不必重新扫描整个项目；
- 能明确知道新增还是修改、在哪些目录、实现什么业务结果、依赖什么以及如何验收；
- 完成后可以单独提交、检查或联调；
- 不需要在计划中指定类名、方法名、算法伪代码或逐行实现。

如果任务只写“完成页面”“实现接口”“新增数据库表”，说明过粗；如果任务开始规定具体函数、变量或代码片段，说明过细。

## 常见错误

- 把模块拆成前端、后端、数据库三个业务模块；
- 把每个原型页面都拆成独立模块；
- 模块名称宏大，但没有业务对象、状态和完成输出；
- 任务只有动作词，没有目录、输入、输出和验收；
- 前端计划重复接口字段，后端计划重复全部 DDL；
- 为追求简洁强制限制任务数量，导致多个独立结果塞入同一条；
- 为追求详细写到类、函数、SQL 执行步骤，变成实现方案而不是开发计划。
