## 通用规则

使用业务模块名，不使用“前端模块”“Controller 层”作为一级模块。模块按依赖先后排列；最终计划不再单独绘制依赖图。真实目录直接写路径，尚未创建的目录加 `[拟建]`。

证据状态只使用：`代码证据`、`需求明确`、`用户确认`、`拟建建议`。计划项使用动宾短语，每个模块通常 2 至 4 项，不写逐函数步骤。

控制输出长度：

- 模块确认稿中每个模块最多 4 行，只保留目标、范围、顺序原因和证据。
- 整体计划只保留一张模块表、最多 3 个管理检查点和范围外清单。
- 前端、后端计划不重复接口字段或数据库字段。
- 接口契约先定义可复用数据结构；端点只写方法、地址、请求参数和响应结构，不默认写 JSON 示例。
- 最终对话只说明暂停原因或给出文件链接，不粘贴已经写入文件的正文。

## 接口契约

文件：`01-api-contract.md`

先写已有代码或用户确认的公共规则：Base URL、鉴权、时间/金额格式、分页和统一响应结构。无法确定且会影响本次接口时先询问。

重复出现在多个接口中的对象先定义一次：

```md
## 数据结构

### {结构名称}

| 字段 | 类型 | 中文说明 |
|---|---|---|
| {field} | {type} | {说明} |
```

每个接口使用相同结构：

```md
## {业务模块}

### {请求方式} {请求地址} — {接口名称}

#### 请求参数

| 位置 | 参数 | 类型 | 必填 | 中文说明 |
|---|---|---|---|---|
| path/query/header/body | {name} | {type} | 是/否 | {说明} |

#### 响应值

`{结构名称}` / `{结构名称}[]` / `{只列本接口特有的少量字段}`
```

字段名、类型、必填性、枚举值和统计口径必须来自需求、现有代码或用户确认。没有请求参数时写“无”，不要生成空表。接口顺序与业务模块计划一致。只有响应嵌套关系无法从数据结构表达时才加入 JSON 示例。不要写控制器实现伪代码。

````md
## 数据库变更

```sql
-- 使用已确认的数据库方言
{CREATE TABLE 或 ALTER TABLE}
```
````

DDL 规则：

- 新表使用 `CREATE TABLE`，已有表变更使用最小必要的 `ALTER TABLE`；不要为已有对象重复建表。
- 沿用现有命名、主键、租户、软删除、审计字段、索引和迁移约定；新系统中这些约定不明确且会改变全局结构时先询问。
- MySQL 在表和字段定义中使用 `COMMENT`；PostgreSQL、Oracle 等使用 `COMMENT ON TABLE/COLUMN`；SQL Server 使用扩展属性语句；SQLite 在相邻 SQL 注释中逐表逐字段写中文说明。
- 每张表必须有中文表说明，每个字段必须有中文字段说明。索引、唯一约束、外键和枚举约束只在业务或现有代码需要时添加。
- DDL 必须能独立辨认方言，不混用多种数据库语法。
