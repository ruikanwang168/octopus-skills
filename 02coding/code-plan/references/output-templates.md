## 文档关联规则

所有文档共用同一套编号：

| 对象 | 编号示例 | 用途 |
|---|---|---|
| 业务模块 | `M01` | 串联整体、接口、前端、后端和数据库计划 |
| 接口 | `API-M01-01` | 标识模块内的接口契约 |
| 单体任务 | `APP-M01-T01` | 演示系统的可执行任务包 |
| 前端任务 | `FE-M01-T01` | 正式系统前端任务包 |
| 后端任务 | `BE-M01-T01` | 正式系统后端任务包 |

业务模块按依赖顺序编号。模块顺序一旦确认，最终文档必须保持相同顺序和名称。真实目录直接写路径；尚未创建的目录加 `[拟建]`。证据状态只使用：`代码证据`、`需求明确`、`用户确认`、`拟建建议`。

简洁只体现在不重复和不写实现代码，不能删掉任务包的目录、输入、输出和验收。整体计划保持短；接口、前端和后端计划保留 AI 开发所需细节。

````md
## 数据库 DDL

```sql
-- 使用已确认的数据库方言
{CREATE TABLE 或 ALTER TABLE}
```
````

DDL 规则：

- 新表使用 `CREATE TABLE`，已有表变更使用最小必要的 `ALTER TABLE`；不要重复创建已有对象。
- 沿用现有命名、主键、租户、软删除、审计字段、索引和迁移约定；新系统中会影响全局结构的约定不明确时先询问。
- MySQL 使用表和字段 `COMMENT`；PostgreSQL、Oracle 使用 `COMMENT ON TABLE/COLUMN`；SQL Server 使用扩展属性；SQLite 在相邻 SQL 注释中逐表逐字段写中文说明。
- 每张表和每个字段必须有中文说明。索引、唯一约束、外键和枚举约束只在业务或现有代码需要时添加。
- DDL 必须能独立辨认方言，不混用语法。

## 输出检查

- 模块编号、名称和顺序在所有文档中一致；
- 每个接口、前端任务、后端任务都能追溯到一个业务模块；
- 每个任务包都有目录、输入、实施要点、输出和验收；
- 前端计划不复制完整接口字段，后端计划不在模块正文重复完整 DDL；
- 另一个 AI 可以从任务包直接开始开发，无需重新拆需求；
- 文档没有类名、函数名、伪代码、人力和工期估算。
