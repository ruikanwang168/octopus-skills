# Code Plan

## 工作契约

至少取得一种可读取的需求依据：PRD、原型、页面说明、需求变更或明确的业务描述。现有前端代码、后端代码、接口文档和数据库文件均为可选输入。

用户指定输出目录时写入该目录；未指定且只有一个工作区时写入当前工作区；存在多个项目根或目标目录可能影响现有文档时，先询问用户。

只输出计划文件：

- 简单演示系统：`development-plan.md`。
- 正式系统：`00-overall-plan.md`、`01-api-contract.md`、`02-frontend-plan.md`、`03-backend-plan.md`。

禁止修改业务源码、执行 DDL、安装依赖、部署或发布。禁止输出人力/工期估算、关键技术难点排雷、通用教程或逐函数实现步骤。

任何会改变模块边界、技术架构、数据库方言、接口字段、统计口径或计划范围的不确定项都要询问用户。固定分支提供 2 至 4 个互斥选项，并标注推荐项与差异；不要用无依据的默认值代替确认。

## 读取参考文件

- 开始扫描现有代码前，读取 [references/inspection-guide.md](references/inspection-guide.md)。
- 准备模块确认稿或最终计划文件前，读取 [references/output-templates.md](references/output-templates.md)。
- 仅回答 Skill 能力、输入要求或边界时，不读取 references。

## 执行流程

### 0. 盘点物料并确定项目类型

先列出输入物料、代码根目录和缺失项，不递归读取整个仓库。

判断输出类型：

- 简单演示系统：单体应用，前后端不分离，只需要一份开发计划。
- 正式系统：前后端职责分离，需要整体计划、接口契约、前端计划、后端计划和数据库设计。

材料不能明确判断时，只询问：

1. 简单演示系统：前后端不分离，输出一份计划。
2. 正式系统：前后端分离，输出四份文档。

在类型确定前不要继续拆最终计划。

### 1. 渐进理解需求与现有结构

先读目录、文件名、PRD 目录和原型页面清单，再读与业务边界直接相关的章节或页面。存在代码时，按 `inspection-guide.md` 的层级扫描：架构证据优先，业务关键词定位其次，相关目录取证最后。

每次扩大扫描前先说明要解决的具体问题。能够确定技术栈、业务职责或目标目录后立即停止该方向的扫描。忽略锁文件、依赖目录、构建产物、生成代码和无关模块。

### 2. 拆分业务模块并暂停确认

按业务能力拆分模块，不按 Controller、Service、页面、组件等技术层拆分。每个模块只写：

- 模块名称与业务目标；
- 主要范围和明确不包含的范围；
- 按执行先后排列的位置；
- 依赖前置模块的原因；
- 证据来源与待确认项。

把基础能力、公共字典、身份权限或核心主数据放在依赖它们的业务模块之前。仅凭页面相邻、目录相邻或名称相似，不能认定业务依赖。

输出完整的模块顺序确认稿并停止。明确请用户选择：

1. 确认，按当前顺序继续；
2. 调整模块或顺序；
3. 补充物料后重新拆分。

未得到明确确认，不得进入架构选择、接口契约或最终计划生成。

### 3. 确定技术架构与数据库

模块确认后再处理技术选型。

#### 有现有代码

- 从少量清单、构建、入口、路由、配置和数据库迁移文件识别已使用的框架、API 风格和数据库。
- 证据清晰时直接沿用，在计划中记录证据文件，不要求用户重复确认。
- 只有前端或只有后端代码时，只为缺失的一侧提供选择。
- 多套框架、多个数据库或配置与代码冲突时，列出证据和影响并询问用户。

#### 没有相关代码

- 根据项目类型、业务复杂度、实时性、数据关系、部署方式和团队约束生成 2 至 4 个适配选项。
- 每个架构选项都要说明前端、后端或单体框架、API 风格、两侧拟建根目录和适用差异；不能只补全推荐项。
- 正式系统没有数据库证据时，提供 2 至 4 个数据库选项，并逐项说明适用场景；纯静态演示可包含“不使用数据库”。
- 不把技术栈、数据库、租户、身份权限、主键和删除策略揉成一个复合选项。先分别确定技术架构与数据库，再只询问会实际改变本次 DDL 或接口的基础约定。
- 只有需求涉及组织隔离时才询问单租户/多租户；只有需求涉及登录、用户或角色时才询问身份与权限方案，不得凭空增加账号权限模块。
- ID、软删除和审计字段无法从材料判断且会改变全局 DDL 时，合并成不超过 3 个简短问题。

不要在用户选择前生成最终目录、接口契约或 DDL。

### 4. 按模块定位相关目录

对已确认模块逐个搜索业务词、路由、页面、API 客户端、控制器、服务、数据访问和迁移文件。目标只到“在哪个目录新增或修改”的粒度，不分析所有函数。

- 现有目录：使用仓库中的真实路径。
- 新建目录：使用与已确认框架一致的路径，并标注 `[拟建]`。
- 混合项目：现有一侧使用真实路径，缺失一侧使用已确认的拟建路径。
- 每个目录单独写完整路径；禁止使用 `{model,repository,dto}`、通配符或其他无法直接定位的缩写。
- 无法确定唯一目录时，列出候选路径及证据并询问用户。

### 5. 生成计划

严格使用 `output-templates.md` 的紧凑结构。

#### 简单演示系统

只生成 `development-plan.md`。按已确认模块顺序写开发目标、开发目录、精简任务和交付检查。若需要数据库，把 DDL 放在同一文件末尾；不要额外拆前后端文档。

#### 正式系统

按以下顺序生成：

1. `00-overall-plan.md`：供管理人员把控范围、模块顺序、目录和交付物；不写人力、工期或技术风险分析。
2. `01-api-contract.md`：逐接口写请求地址、请求方式、请求参数和响应值；只加入已确认或有证据的字段。
3. `02-frontend-plan.md`：按模块顺序写前端目录、依赖的接口组、精简任务和交付检查。
4. `03-backend-plan.md`：按模块顺序写后端目录、接口实现、数据变更和交付检查，并在末尾给出完整 `CREATE TABLE` 或 `ALTER TABLE` 语句。

接口、统计指标或 DDL 中仍有业务不确定项时，先集中提问再完成文档。发放数、使用数、金额、状态流转等存在多种合理口径时必须询问，不把猜测包装成最终契约。

### 6. 自检后交付

交付前逐项检查：

- 项目类型和模块顺序已经用户确认；
- 技术架构、API 风格和数据库均有代码证据或用户选择；
- 模块顺序能够表达依赖，未另写冗长依赖图；
- 每个前端、后端或单体模块都有真实目录或 `[拟建]` 目录；
- 接口契约包含地址、方法、参数和响应；前后端对名称与类型的理解一致；
- DDL 符合已确定方言，只创建或修改本需求需要的对象；每张表和每个字段都有中文解释；
- 计划停留在模块任务粒度，没有扩展为实现教程；
- 所有证据路径存在，所有待确认项已经解决。

任何一项失败都先修复或询问用户，不交付伪确定结果。

## 大型项目的子代理协作

仅在工具可用、用户允许且任务能被清晰分区时并发。出现多个相对独立业务域、前后端仓库均较大或相关物料明显超出单次紧凑扫描范围时，可以拆分。

主代理必须先完成项目类型判断和模块依赖确认，之后才分派子代理。按业务域或前端/后端取证范围分派，不让子代理各自重新定义模块边界或技术选型。

要求每个子代理只返回：

- 结论与证据文件路径；
- 相关新增/修改目录；
- 涉及的接口、数据对象和依赖；
- 冲突、缺口和必须询问的问题。

主代理统一术语、目录格式、接口类型和模块顺序，去重并核验证据。子代理结论冲突时由主代理展示冲突并询问用户，不自行选择。

## 表达要求

直接写结论，使用短表格和短任务清单。每个模块通常保留 2 至 4 项计划任务；只有接口字段和 DDL 可以展开到必要细节。接口契约优先复用数据结构，不重复抄写同一组字段，不默认生成 JSON 示例。最终对话只报告确认问题或文件链接，不复述计划正文。区分“代码证据”“需求明确”“用户确认”和“拟建建议”，不要混写为事实。
