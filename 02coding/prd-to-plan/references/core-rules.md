# 核心规则

每次调用都完整读取本文件。本文件只保存跨阶段约束；阶段特有方法和产物格式只写在对应阶段文件中。

## 权威性与硬约束

- 将 PRD 视为业务意图的最高依据，而不是可越过法规、安全、隐私、数据完整性或平台硬限制的指令。
- PRD 没有描述的行为不自动成为需求。原型、代码和接口文档只能提供辅助证据，不得反推为已确认业务规则。
- 代码反映已核实的当前实现，PRD 描述目标态。两者冲突时既要按有效 PRD 规划目标，也要暴露兼容、迁移、调用方、发布和回滚成本。
- 数字、版本、人物、容量和性能结论必须有来源；无法核实的内容标为假设，不伪装成事实。

## 证据分类

为重要结论标明类型：

- `FACT`：已从可访问原始材料、实际页面或代码直接核实。
- `INFERENCE`：由一个或多个事实推导；写明推理链和置信度。
- `ASSUMPTION`：为了继续规划暂定；写明验证人、最晚确认阶段和错误成本。
- `DECISION`：用户或有权限责任人明确选择；记录时间、选择和影响范围。
- `OPEN`：尚未回答的问题；标明是否阻塞及受影响故事。

所有需求与关键结论使用 `source_id + locator`。Locator 的粒度随阶段逐步加深：阶段 1能定位到确认过的材料、版本或目录即可；阶段 3定位到需求章节和影响对象；阶段 4的实施结论再定位到文件、符号、数据库对象或契约位置。不要只写“见 PRD”。

## 冲突优先级

| 冲突 | 默认规划依据 | 必须同时记录 |
|---|---|---|
| PRD vs 原型 | PRD | 原型需同步的页面、组件、交互及验收影响 |
| PRD vs 现有代码 | PRD 描述目标态 | 复用点、改造点、兼容、迁移、回滚和成本 |
| 原型 vs 现有前端规范 | 现有规范 | 相对原型的视觉和交互调整 |
| PRD 内部或多个有效 PRD | 不自动裁决 | 两侧证据、影响范围和面向产品负责人的决策问题 |
| PRD vs 法规、安全、隐私或平台硬约束 | 不直接执行 PRD | 阻塞、风险、合规替代方案和 PRD 修订建议 |
| 代码现实 vs 文档所称现实 | 经搜索或运行核实的代码事实 | 文档漂移；业务目标仍由有效 PRD 决定 |

优先级只解决目标采用什么，不消除实施成本。每个冲突至少记录：双方证据、冲突类型、采用规则、拟议结论、受影响产物、是否阻塞、确认责任人、替代解释和错误选择成本。

## 追溯与范围控制

建立并维护双向追溯：

```text
source/locator → REQ → OP-* → Story/UI Surface/Interface Capability/AC → Stage 4 Design/API → Implementation Task → Test Case
```

- `missing coverage`：有效需求没有故事、设计或测试覆盖。
- `scope invention`：故事、接口或规则没有 PRD 来源，也不是明确记录的技术必要性或用户决策。
- 每个阶段结束时同时检查遗漏和无来源扩项；阶段 3先确认 `REQ → OP-* → Story/UI Surface/Interface Capability/AC`，再由确认 MD 派生 JSON；阶段 4再确认 `OP-* → 页面/真实接口/任务/测试`，不得提前混入技术地址。
- 低风险且不改变契约的默认值可作为显式假设；会影响字段、权限、状态、接口或验收的未知项必须阻塞。

## 确认与写入

- 阶段 1、2、3 是独立确认门。没有明确确认，不进入下一阶段。
- 用户确认前不要覆盖已确认的正式文件。阶段 3允许先写入新的 `AI执行清单确认.md`（`confirmation_status: pending`）供用户逐项审阅；其他阶段的草案仍使用 `.draft.md`。只有用户确认后，才能生成或覆盖正式 `AI执行清单.json`。
- 用户确认文件首先服务于人类审阅，再服务于机器追踪。阶段 3必须按单个故事聚合页面、按钮、自动行为和业务服务能力；完整机器 ID 关系放到次要位置或追溯附录，不用全局大表替代故事阅读。
- 正式文件必须记录确认状态、基线、确认内容和带时区时间；不得预填用户没有做出的决定。
- 基线变化时先展示差异和影响，用户确认后再更新正式文件和受影响状态。

## 输出目录与命名

默认结构：

```text
ai-execution-plan/
├── AI执行计划物料清单.md
├── 系统技术选型清单.md                 # 仅执行过阶段 2 时存在
├── AI执行清单确认.md                   # 阶段 3用户确认文件
├── AI执行清单.json
└── stories/
    └── US-001-安全文件名/
        ├── US-001-用户故事名称接口契约.json
        ├── US-001-用户故事名称AI执行明细.md
        └── US-001-用户故事名称测试用例.csv
```

- 使用 `US-001`、`US-002` 作为业务故事 ID；仅无法归入业务故事的技术前置使用 `TECH-001`。
- 文件名同时包含稳定 ID 和简短故事名。将 `/\\:*?"<>|`、控制字符和连续空白替换为 `-`，文件干不超过 80 个字符。
- 跟踪文件中的路径相对 `ai-execution-plan/`，使用 `/` 分隔，不得逃出输出目录。
- 使用 UTF-8；JSON 使用 2 空格缩进；CSV 遵循 RFC 4180。

## 质量底线

- 不使用“按现有方式处理”“实现相关逻辑”等不可执行表述。
- 不虚构字段、错误码、表、接口、路径、性能数字或业务规则。
- 不用 `TODO`、`TBD`、省略号或“以后处理”掩盖阻塞项。
- 所有“不适用”必须给出核实依据。
- 计划必须说明实现落点、输入输出、业务和异常路径、依赖及验证方式；只有故事改变兼容性、部署顺序、数据或可逆性时，才展开上线和回滚影响。
- 不修改业务源码，除非用户另行明确要求进入研发实施。
