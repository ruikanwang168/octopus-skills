## 阶段边界

阶段 1只回答：本次后续规划以哪些资料为依据，这些资料在哪里、是否可访问、采用哪个版本、分别具有什么权威性，以及哪些资料冲突需要用户确认。

本阶段不承担以下工作：

- 不做完整 PRD 需求拆解或用户故事拆分。
- 不检索完整前后端调用链，不判断每项功能的复用、改造或替换方案。
- 不确定页面、接口、数据库对象、事件或任务的影响集合。
- 不做数据库设计、接口设计、技术选型或实施任务规划。
- 不为证明“可以直接开发”而提前执行阶段 3或阶段 4的分析。

允许进行的检查仅限于确认材料身份、位置、基本版本、可访问性、权威关系和明显冲突。代码符号、调用链、页面和接口等精确实现定位留到对应用户故事的后续分析。

## 进入与退出条件

进入条件之一：

- 没有已确认的 `AI执行计划物料清单.md`。
- 用户新增、更换、删除或排除了 PRD、原型、代码、数据库脚本或辅助材料。
- 物料指纹、代码提交、数据库基线或在线内容版本发生变化。
- 既有清单引用的材料无法访问，无法确认范围和基线是否仍有效。

PRD 或等价的明确需求基线是必需核心材料。没有时停止并请求提供，不用原型、代码或数据库反推产品需求。

退出条件：用户明确确认纳入和排除的物料、材料权威关系、需要决策的冲突、数据库基线状态和下游读取入口，随后生成 `confirmation_status: confirmed` 的正式清单。

## 必须确认的物料范围

主动发现并向用户确认以下材料是否纳入本次规划：

- PRD 文件、在线地址、补充 PRD、变更记录和附件。
- 可运行原型、原型地址、设计稿或交互说明。
- 现有前端代码及其代码规范、组件库或设计系统。
- 现有后端代码及其基础框架和工程约束。
- 现有系统的全量数据库脚本或能够完整重建当前数据库结构的基线。
- 现有接口文档、外部系统文档、数据字典及其他辅助材料。

### 全量数据库基线

- 对已有系统或增量项目，必须确认现有全量数据库脚本的位置。可接受完整建库建表脚本、当前结构导出，或能够从空库完整重建当前结构的迁移脚本链。
- 只有零散增量 SQL、实体类、Mapper、ORM 定义或部分迁移文件时，不能写成“已提供全量数据库基线”；应说明当前只有部分材料，并请求用户提供完整基线。
- 如果没有发现全量数据库脚本，必须询问用户提供其位置；因权限暂时不可访问时记录访问限制，并阻塞依赖现有数据结构的后续范围。
- 只有用户明确确认这是全新项目、没有需要继承或迁移的现有数据库时，才可以记录“全量数据库脚本不需要提供”。不能因为没有搜到数据库脚本就自行判定为全新项目。
- 全新项目可以在后续阶段设计数据库；阶段 1不提前生成表结构或 SQL。

如果用户没有说明项目是全新还是增量，且材料本身也无法确定，应先询问项目类型和数据库基线情况，再确认正式物料范围。

## 各类物料的基本核实

| 来源 | 阶段 1只核实 | 不在阶段 1推断或展开 |
|---|---|---|
| PRD 文件 | 路径、标题、版本或日期、可访问性、是否纳入 | 完整需求拆解、故事边界、页面接口集合 |
| 在线 PRD | 最终 URL、访问时间、版本或更新时间、访问限制 | 只凭标题或搜索摘要复述正文 |
| 原型或设计稿 | 位置、访问方式、是否可运行、版本依据、参考用途 | 原型字段和模拟接口已经成为业务契约 |
| 前端代码 | 仓库或目录位置、分支、提交、工作区状态、是否纳入 | 完整路由/组件检索和复用改造方案 |
| 后端代码 | 仓库或目录位置、分支、提交、工作区状态、是否纳入 | Controller 到数据库的完整调用链和业务覆盖判断 |
| 全量数据库基线 | 脚本或迁移目录、数据库类型/版本（可取得时）、完整性、可访问性、是否可重建当前结构 | 新表设计、字段变更和迁移方案 |
| 接口及辅助文档 | 位置、版本、所属环境、可访问性、用途 | 文档与当前代码或生产环境必然一致 |

基本核实规则：

- 为每项纳入材料分配稳定 `source_id`。建议使用 `PRD-001`、`PROTO-001`、`FE-001`、`BE-001`、`DB-001`、`AUX-001` 等统一三位编号。
- 本地文件记录项目相对路径和可取得的版本或指纹；在线材料记录 URL、访问时间、版本或更新时间和访问限制。
- Git 信息只能归属于实际仓库。记录某个目录的 Git 分支、HEAD 或 dirty 状态前，先确认该目录属于哪个仓库根；若 Git 解析到父目录，应明确写成父工作区上下文，不能把父仓库版本冒充该目录自己的版本。
- 非独立 Git 的原型或代码目录只记录目录位置和当前快照依据，不虚构分支、提交或工作区状态。
- 阶段 1的 locator 以能找到材料本身为准，例如文件路径、目录、URL、仓库与提交或数据库脚本目录；不强制定位到类、函数、页面或接口符号。
- PDF、DOCX、表格、图片等按真实格式确认可访问性；只有在无法判断材料身份和范围时才做必要的最小读取。

## 冲突确认策略

阶段 1只处理能够从材料范围和基本内容直接识别的冲突，不为了寻找全部冲突而深度扫描代码。

- PRD 与原型存在展示、命名或交互差异时，默认以 PRD 为业务依据，记录原型后续需要同步的点；不重复让用户选择权威来源。
- PRD 与现有代码不一致时，记录“PRD 是目标态、代码是当前实现”。兼容、迁移、改造和回滚方案留到后续阶段，除非它们会反过来改变本次纳入范围。
- 原型与现有前端规范冲突时，以现有规范为准，记录后续需要调整的表现形式。
- 会改变业务范围、角色、权限、字段、状态、页面流程、接口契约、数据库范围或验收结果的冲突，必须展示双方材料位置和影响，让用户确认。
- PRD 内部冲突、多个有效 PRD 冲突，以及法规、安全、隐私或平台硬限制冲突，不得自动裁决。
- 仅影响实现细节、且不改变本轮物料范围和业务结论的问题，记录为后续阶段待分析项，不在阶段 1展开方案。

需要用户确认的冲突至少说明：双方材料、冲突内容、默认优先规则、建议采用的业务结论、影响范围和未确认是否阻塞。

## 执行步骤

1. 发现用户提供或当前项目中可见的 PRD、原型、前端代码、后端代码、全量数据库脚本和辅助材料。
2. 判断这是全新项目、已有系统增量项目，还是暂时无法确认；据此确定全量数据库基线是否必须提供。
3. 在对话中列出拟纳入、拟排除和缺失的材料，请用户纠正范围。
4. 为纳入材料分配稳定 `source_id`，记录位置、基本版本、可访问性、业务权威性和后续用途。
5. 识别材料之间已经显现的冲突，按本阶段策略区分自动采用、需要用户确认和留到后续分析的事项。
6. 给出下游 AI 的有序读取入口：先读什么、材料用于什么、后续在哪个阶段继续深入。
7. 根据现有技术基线是否已经明确，标记阶段 2需要执行、局部执行或可跳过；不在阶段 1完成选型本身。
8. 在对话中展示拟写入的物料范围、数据库基线状态、冲突结论和下一阶段路由。
9. 用户确认前不写正式文件；用户明确要求保存草案时才写 `.draft.md`。
10. 用户确认后生成或更新正式清单。

分析过程遵循：

```text
发现材料 → 判断项目类型与数据库基线要求
→ 确认纳入/排除范围 → 核实位置/版本/可访问性
→ 确认权威关系与明显冲突 → 形成下游读取入口
→ 等待用户确认
```

## 输出信息要求

正式清单的章节名称、顺序和表现形式不固定。可以使用章节、列表、卡片或局部表格；不要为了满足模板硬生成不适用内容。

无论采用什么结构，必须让用户和下游 AI 快速获得：

- 本次纳入与排除的材料范围，以及尚缺少什么材料。
- 每项纳入材料的 `source_id`、类型、位置、基本版本或快照依据、可访问性、权威性和后续用途。
- 项目是全新还是增量；现有全量数据库脚本的位置与完整性，或者全新项目不需要提供的用户确认。
- PRD、原型、前端代码、后端代码、数据库基线和辅助文档之间的权威关系。
- 已发现冲突、采用结论、是否经过用户确认，以及留到后续阶段处理的事项。
- 下游 AI 的有序首读路径和各材料的使用目的。
- 阶段 1确认内容、带时区时间和下一阶段路由。

阶段 1清单不要求包含 `REQ-###` 需求明细、代码复用矩阵、完整调用链、页面影响集合或接口影响集合。若为了阅读方便使用文档级 `REQ` 编号，必须明确它只是 PRD 文档索引，不是用户故事或最终需求粒度。

## 物料清单规范

正式文件：`AI执行计划物料清单.md`  
可选草案：`AI执行计划物料清单.draft.md`

文件开头保留可机读元数据：

```yaml
---
artifact: "material-manifest"
schema_version: "1.1"
confirmation_status: "pending"
baseline_id: "BL-YYYYMMDD-001"
confirmed_at: null
step_2: "required"
---
```

- `confirmation_status` 仅为 `pending` 或 `confirmed`。
- 当前物料清单 `schema_version` 使用 `1.1`。旧 `1.0` 没有明确区分资料范围与深度实现分析，也没有强制记录项目类型和全量数据库基线；再次调用时必须回到阶段 1补充并由用户重新确认，不能自动升级。
- `step_2` 仅为 `required`、`confirmed` 或 `skipped_existing_stack`。
- 草案使用 `pending`；正式文件使用 `confirmed`、实际确认时间和稳定基线 ID。
- `step_2: confirmed` 表示已经完成本次需求的技术能力分析并取得用户确认，即使结论是“不新增框架，沿用现有技术栈”。`skipped_existing_stack` 仅为旧清单兼容状态或用户明确要求沿用既有、且本次没有新的技术分析范围时使用；不能仅因为发现了任意前端或后端代码就跳过阶段 2。

本地文件可记录 SHA-256；Git 仓库记录实际仓库根、远端、分支、完整 HEAD 和 dirty 状态；普通目录记录目录位置和快照依据；在线材料记录规范化 URL、访问时间、版本或更新时间和访问限制。

## 完成检查

- PRD 或等价需求材料真实可访问并已纳入；不可访问时已请求用户提供导出或授权。
- 所有已发现材料都明确为纳入、排除或缺失，没有只在正文提到却未进入物料范围的前端、后端、原型或数据库材料。
- 每项纳入材料有稳定 `source_id`、位置、基本版本或快照依据、可访问性、权威性和用途。
- 已确认项目是全新还是增量。已有系统已提供可重建当前结构的全量数据库基线；未提供时已请求用户补充并阻塞受影响范围；全新项目不要求提供时有用户明确确认。
- Git 版本没有错误归属于非独立仓库目录。
- 已发现的材料冲突按默认规则记录，所有会改变范围或业务结论的冲突已由用户确认。
- 深度需求拆解、代码调用链、页面接口影响和数据库设计没有被提前塞进阶段 1。
- 下游 AI 有明确、按顺序的材料读取入口，并能知道每类材料在后续阶段中的用途。
- 阶段 2的执行、局部执行或跳过结论有基本材料依据，但没有在阶段 1提前完成架构选型。
- 用户已明确确认正式物料范围，元数据、正文和确认记录一致。
