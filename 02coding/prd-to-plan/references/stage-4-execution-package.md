## 目标

执行包交给一个不了解前序讨论、但能阅读代码并自主开发的 AI。它读完后应能立即定位背景和代码，理解数据库、接口、页面及业务规则，按顺序实施并验证结果；不需要替规划者补产品规则、选择业务数据来源、猜测接口交互顺序或重新决定代码所属模块。

遵循一句话：**考虑要穷尽，输出要适用，描述要具体，结构要自由。**

- “考虑完整”是指生成前逐项检查可能影响实现和验收的因素。
- “输出完整”是指所有适用信息都写清，而不是篇幅长或章节多。
- 不固定执行明细的章节名称、数量和顺序。
- 不适用的信息直接省略，不生成空章节或成片 `N/A`。
- 删除框架常识、重复契约、通用质量口号和执行 AI 可由代码自然发现的普通细节。
- 详细不等于可执行。内容再多，只要关键字段无来源、页面动作没有可调用能力、代码落点未决定或验证命令不可运行，就仍是草案。

## 进入和退出

进入前必须存在已确认且有效的 `AI执行清单.json`，且其 `catalog_confirmation_document` 与 `catalog_confirmation_hash` 仍对应已标记 `confirmation_status: confirmed` 的确认 Markdown。当前故事必须包含用户确认的 `operation_refs`、`ui_surfaces` 和 `interface_capability_refs`；每个引用都能回到 `prd_operation_catalog` 或 `interface_capability_catalog`。阶段 4在检索现有前后端代码后，将业务接口能力映射为真实页面、路由、接口和数据库影响集合；阶段 3的 `INT-*` 不是可直接调用的 HTTP 契约。当前故事依赖已满足，并且不存在会改变字段、权限、页面流程、数据或接口契约的未决问题。

默认一次只处理一个故事。用户指定且依赖允许时按指定故事处理，否则选择最早的 `plan_generated=false` 或 `plan_stale=true` 故事。

只有接口契约、执行明细和测试用例互相一致，同时通过本文件的直接开发语义核验和 `tracker.py validate --check-artifacts`，才能设置 `plan_generated=true`。脚本校验是必要条件但不是充分条件。

阶段 4 检索后发现会改变业务行为、页面流程、字段、接口、数据来源、权限或验收的未知项时，先把证据、影响和最小决策问题发给用户。没有结论前可以保留 `.draft.md`，但不得生成可被误认为正式执行基线的完整包，也不得把 `plan_generated` 设为 `true`。不要用“实施时确认”“按现有规范复核”把架构决定转移给下游 AI。

## 生成前的完整思考清单

这一节是 AI 的内部分析过程，不是执行明细的固定目录。逐项检查后，只把适用结论写入执行明细。

### 背景和检索上下文

- 用户故事解决什么问题，角色、目标结果、范围内外、依赖和 `REQ/AC` 是什么。
- 当前故事的每个 `OP-*` 具体表示哪个 PRD 按钮、查询、状态变化或自动动作，以及它对应的 `ui_surface`。
- PRD 的文件或 URL、章节、页码或锚点在哪里。
- 原型的页面、路由、组件或交互位置在哪里。
- 前端入口、路由、页面、组件、状态、请求封装和测试在哪里。
- 后端 Controller/Handler、Service、Domain、Repository/Mapper/Client、DTO 和测试在哪里。
- 表、迁移脚本、缓存、事件、任务和外部系统配置在哪里。
- 为完成当前故事，要先学习哪些依赖用户故事、已有执行包、共享契约和相关代码。
- 每个位置为什么要读，已核实了什么，准备复用、修改、新建、删除还是仅参考。
- 对增量项目，先核实真实的工程约定：模块边界、网关或请求前缀、鉴权与租户传递、统一响应包装、错误模型、分页模型、ID/时间/软删/审计字段、数据库迁移方式和测试入口。只记录当前故事实际用到的约定。
- 代码定位优先到具体文件与符号。目录只能作为搜索起点，不能作为最终代码落点；新文件也要确定所属模块、包或相邻实现依据。
- 声称复用组件、请求封装、接口、表或工具前，必须打开实现核实它确实提供所需能力；名称相似或处于同一目录不构成复用证据。

不存在的材料不要虚构；无法访问且会改变设计时标为阻塞。

### 数据和数据库

- 是否新增、修改或删除表、字段、索引、约束、视图或初始化数据。
- 字段类型、精度、默认值、空值、唯一性、关系、软删和数据生命周期是否明确。
- 是否需要历史数据回填、数据转换、双读双写、在线迁移或兼容窗口。
- 正向 SQL、回滚 SQL、数据库方言、执行顺序和校验方法是否完整。
- 哪些接口、事件或任务读写这些数据，数据域、事务、锁和并发规则是什么。
- 每个页面展示、接口响应和业务判断字段来自哪一列、哪次计算、哪个既有服务或哪个外部系统；新增表的数据由谁、在什么时机写入或初始化。
- 新表不能只描述读取方式。若故事依赖初始数据、配置数据或上游同步，必须同时落定种子数据、迁移、管理入口、同步任务或明确依赖故事；否则数据链路未闭合。
- SQL 的字段名、类型、主键、租户、审计时间、软删和版本字段应与现有工程基线一致。若业务目标确实要求偏离，记录依据、兼容影响和已确认决策。

### 后端接口和其他服务入口

- 本故事涉及哪些复用、新增、修改、废弃或删除的 HTTP 接口。
- 每个接口的稳定契约 ID、Method、Path、消费者、调用时机和结果用途是什么。
- 每个接口对应哪些需求和 AC，要先学习哪些后端和契约代码。
- 权限、租户或数据域、输入转换、业务校验、查询、计算、写入、状态变化和副作用是什么。
- 事务、幂等、并发、重试、回滚、补偿、成功结果和错误语义是否明确。
- 删除或废弃接口的替代接口、调用方迁移和移除时机是否明确。
- 是否还涉及事件、消息、定时任务、批处理、文件处理、搜索索引或外部系统；不要把这些强行伪装成 HTTP 接口。
- 页面需要“先查询影响再确认修改”时，查询与修改必须在契约上形成可执行的调用顺序；不能让修改接口在修改成功后才返回确认前需要的数据。
- 对每个请求字段、响应字段、错误和并发令牌核对产生者与消费者。页面或后续调用需要的字段必须真实出现在契约中，契约字段必须有确定的数据来源。
- 增量项目的 Method/Path、服务前缀、请求头、认证上下文、统一响应包装、分页和错误结构必须遵循已经核实的项目约定；不能为当前故事另造一套传输规范。

### 前端页面和用户交互

- 涉及哪些复用、新增、修改或删除的页面、弹窗、抽屉和嵌入区域。
- 每个页面的类型、路由、入口、可复用组件、布局区域、状态和权限是什么。
- 列表是否分页，分页方式、页大小、默认排序、数据源、加载、空、失败状态是什么。
- 列表显示哪些列、顺序、格式、空值、权限、行交互和操作是什么。
- 有哪些查询条件，顺序、控件、默认值、精确/模糊/范围匹配、校验和请求映射是什么。
- 表单有哪些字段，顺序、分组、组件、默认值、显示/隐藏、只读/编辑、校验、联动和错误映射是什么。
- 按钮、行操作、批量操作、菜单和自动动作的可见、可用、执行前校验、确认、防重复、请求、成功和失败行为是什么。
- 初始化、编辑、提交、取消、未保存离开、刷新、无权限、并发冲突等业务相关交互是否明确。
- 每个动作按时间顺序列出所需数据和接口调用。确认框、按钮可用性或下一步跳转依赖的数据，必须能在相应动作发生前取得。
- PRD 已明确的路由、布局、字段、顺序、校验、实时性和空态必须原样进入目标设计。分页、长度上限、默认值、缓存或额外确认等 PRD 未定义行为，只能来自现有强制规范、可说明的技术必要性或用户决策，不能静默补充。

不要描述每个无业务意义的点击；需要写全的是会影响数据、状态、权限和验收的交互。

### 实施和验收

- 改哪些仓库、文件、类、函数、组件、表和配置，执行顺序及依赖是什么。
- 每项任务完成条件、验证命令和可观察结果是什么。
- 每个 AC 是否能映射到页面、接口、数据、任务和测试。
- 是否存在遗漏需求、无来源扩项、跨故事冲突或未解决阻塞。
- 增量项目的任务落点是否具体到真实存在或已确定新建的仓库、模块、包、文件和符号；是否仍要求下游 AI 决定“放哪个模块”。
- 验证命令是否从当前仓库的构建文件、脚本或测试配置中核实，能够在相应工作目录实际运行；不要凭技术栈猜命令。
- 测试级别是否与步骤一致；跨故事结果只有在本故事包含对应改造任务或已确认依赖时才能成为完成条件。

## 直接开发语义核验

这是生成正式产物前必须执行的内部核验，不是要求执行明细采用固定章节或增加一张大表。根据故事选择段落、局部表格、伪代码或流程描述，只要下列关系能被明确回答。

### 需求与设计边界

- 将关键结论区分为已核实事实、由事实推导的设计、用户已确认决定和阻塞问题。
- 逐项对比 PRD 与目标设计。任何新增限制、分页、默认值、路由变化、字段删减、状态变化或额外操作都必须有来源；没有来源就是 `scope invention`。
- PRD 与现有代码冲突时，目标行为仍以 PRD 为准，但迁移、兼容、调用方和数据成本必须进入任务；不能通过沿用旧代码静默降低需求。

### 交互与接口闭环

对每个页面动作和自动行为，从触发到完成顺序核对：

```text
前置状态 → 所需数据 → 调用能力/纯前端处理 → 成功状态 → 失败/取消/并发分支
```

- 每一步所需数据必须在该步骤之前已经由页面状态或明确接口取得。
- 每个页面调用的 `contract_id` 必须存在；每个 HTTP operation 必须有真实消费者和调用时机。
- 查询、预检查、确认和修改的先后顺序必须可由契约实现。一个 operation 可以服务多个动作，但不能承担时间上互相矛盾的职责。
- 页面声明的请求字段、并发版本、选项、权限和展示字段必须存在于 OpenAPI；OpenAPI 返回内容必须被页面、任务或其他明确消费者使用。

### 字段与数据闭环

对影响页面、业务判断、接口或验收的字段建立双向关系，表达方式自由：

```text
PRD 字段/规则 ↔ 页面字段或动作 ↔ OpenAPI schema/path ↔ 后端 DTO/计算 ↔ 表字段/既有服务/外部来源
```

- 任一方向断开都要修正或标为阻塞。尤其核对列表排序字段、状态、版本号、引用数、枚举、租户和审计字段。
- 新增或修改数据库时，除了 DDL，还要闭合创建、初始化、更新、查询、回填和回滚中实际适用的链路。
- 数据来自依赖故事或外部系统时，引用其稳定契约和就绪条件；不能用尚未定义的“上游数据”作来源。

### 现有工程适配

- 用实际源码核对接口前缀、请求头、响应包装、异常结构、分页对象、ID 与时间类型、ORM/迁移方式、权限和租户上下文。
- 用实际组件 API 或相似业务页面核对复用结论；不具备目标能力的组件不能被写成复用基础。
- 为每项任务确定真实模块和相邻实现。可以让执行 AI 在已确定模块内选择合理的新文件名，但不能让它重新做模块归属或跨服务边界决策。

### 可验证性

- 验证命令来自当前仓库实际存在的脚本、构建配置或测试框架，并写明工作目录和预期结果。
- 测试步骤与 `test_level` 一致；页面操作通常不是纯 API 用例，接口用例也不应要求未运行的前端回滚。
- 每个关键流程至少覆盖成功和与其风险相称的失败、权限、边界、幂等或并发行为；不机械凑类型。

核验结束时必须得出明确结论：`READY` 或 `BLOCKED`。`READY` 才能生成/覆盖正式三项产物并设置 `plan_generated=true`；`BLOCKED` 时列出证据、影响范围和需要谁决定的最小问题。该结论可以在工作过程和汇报中给出，不强制成为执行明细的固定章节。

## 三项产物

### 接口契约

文件：`[故事ID]-[用户故事名称]接口契约.json`

使用 OpenAPI 3.1.x JSON：

- 根级包含 `openapi`、`info`、`paths`、`components`；`info.x-story-id` 等于当前故事。
- `x-source-references` 每项包含 `source_id`、`locator`、`requirement_id` 和 `acceptance_criterion_id`。
- 每个 operation 有唯一 `operationId`；执行明细把它作为稳定 `contract_id`。
- 每个 operation 有非空 `x-operation-refs`，只引用当前故事的 `OP-*`；同一关系必须出现在操作实现映射和接口标题块的“操作引用”中。
- 每个 operation 写清鉴权、参数或请求体、成功响应、业务错误和通用错误。
- 字段写明类型、格式、必填、约束、枚举、时区和空值语义；分页、幂等、并发版本只在适用时定义。
- 增量项目必须复用已核实的服务前缀、认证/租户头、统一响应包装、分页和错误 schema；若目标态需要改变这些公共约定，先形成架构决策并说明调用方迁移。
- 页面在确认或校验前需要的数据必须由只读查询、预检查 operation 或既有页面状态提前提供；不得只在产生副作用后的响应中返回。
- OpenAPI 中的每个请求字段都有调用方，每个响应字段都有消费者或明确兼容用途；页面和执行明细使用的契约字段不得缺失。
- 复用、新增、修改或当前故事直接消费的接口都进入 `paths`。复用接口也要说明证据。
- 废弃接口保留 `operationId` 并使用 OpenAPI `deprecated: true`，直到调用方迁移完成；执行明细写替代方案和移除条件。
- 故事确实没有 HTTP API 依赖或影响时，`paths` 为空，并用 `x-no-api-change` 写核实依据。
- 事件或 webhook 可使用 `x-event-contracts`；不要为纯异步故事虚构 HTTP 接口。

OpenAPI 只描述外部可依赖行为。Controller、Service、Repository、SQL、事务和算法放在执行明细。

### AI 执行明细

文件：`[故事ID]-[用户故事名称]AI执行明细.md`

标题和顺序由当前故事决定。以下是信息块及其适用条件，不是固定章节模板。

#### 核心：背景和学习索引

用最短文字写清故事背景、目标、范围、依赖、`REQ/AC` 和业务词汇，再给出统一检索索引：

```text
learning_ref | source_type | source_or_repository | location | why_read | verified_finding | planned_use | related_scope
```

- `source_type` 可使用 `prd`、`prototype`、`frontend`、`backend`、`contract`、`database`、`test`、`dependent_story`、`architecture` 或项目需要的补充类型。
- `location` 必须可直接检索：PRD 章节或 URL 锚点、原型路由、文件与符号、表、测试、故事 ID 或执行包路径。
- `verified_finding` 写规划阶段实际核实的事实，不写“开发时再看”。
- `planned_use` 写权威依据、复用、修改、新建、删除或仅参考。
- `related_scope` 关联页面、字段组、`contract_id`、AC 或任务。

增量项目中，最终用于实施的前后端学习项应尽量定位到具体文件与符号；宽泛目录只可作为附加搜索范围。复用结论必须写出已经核实的能力和不能覆盖的部分，不能根据组件名猜测。

每个故事至少包含 PRD 来源。涉及 UI 时包含前端代码或新系统架构入口；涉及接口时包含后端、契约或新系统架构入口。依赖其他故事的实现或契约时，必须包含对应 `dependent_story`。

#### 条件：数据库变更

实际涉及数据库时，写清变更目的、对象、字段与约束、受影响读写链路，并提供符合现有命名、类型和迁移方式的目标方言可执行正向与回滚 SQL。按需补充初始化、种子数据、回填、兼容、锁表、执行顺序和数据校验。

只有 SQL 不够；必须说明 SQL 服务的业务规则、数据由谁写入或初始化，以及被哪些接口、事件或任务使用。依赖一张尚未确认是否存在的表、未定义的上游来源或“实施时再决定”的字段时，数据库设计仍未完成。没有数据库影响时完全省略。

#### 条件：后端接口

OpenAPI `paths` 中存在 operation 时，每个 operation 必须成为一个独立、可定位的接口内容块，不能把多个接口的完整逻辑压进一张全局明细表。标题格式固定，层级可按当前文档选择：

```markdown
### 接口 [createRecord] 创建记录
```

方括号中的 `contract_id` 必须等于 OpenAPI `operationId`，同一故事内唯一。接口索引表可以保留用于概览，但不能替代独立接口块。

阶段 3不提供接口地址基线。阶段 4必须先为每个 `OP-*` 做操作实现决策：是 `frontend_only`、`http_api`、`async_task`、`external_integration`、`database_only`、`navigation` 还是 `mixed`。需要 HTTP 接口的操作必须关联真实 `contract_id`，并在 OpenAPI operation 上用 `x-operation-refs` 反向标记；不需要 HTTP 接口的操作必须写清原因。OpenAPI、接口标题块和“操作实现映射”三者必须一致。

接口标题下先用简短元数据行提供稳定机器可检索信息：

```markdown
- 变更类型：modify
- Method/Path：POST /records
- 操作引用：OP-REQ-001-01
- 服务对象：页面 [record-create] 的提交按钮；成功结果用于跳转详情
- 需求与验收：REQ-001；AC-US-001-01
- 开发前学习：PRD-01；BE-01
- 代码入口与调用链：BE-01：RecordController.create → RecordService.create → RecordRepository.insert
- 契约位置：#/paths/~1records/post
```

- `变更类型` 使用 `reuse`、`new`、`modify` 或 `delete`；废弃兼容期也归入 `delete` 并说明迁移。
- `需求与验收` 后应列出本接口服务的 `operation_refs`，使接口能反查到具体页面动作或自动流程。
- `服务对象` 写页面、按钮、任务或外部调用方，以及调用时机和结果用途。
- `开发前学习` 指向背景和学习索引中需要先读的后端或契约资料。
- `代码入口与调用链` 写可检索的 `Controller/Handler → Service → Repository/Client` 路径和符号，并引用至少一个 `learning_ref`。
- `契约位置` 指向本故事 OpenAPI operation。

随后按接口实际复杂度自由组织，但必须把业务目标和调用背景、按执行顺序的内部业务逻辑、数据访问、成功结果以及适用的权限、输入转换、校验、事务、幂等、并发、回滚、补偿和错误语义写清。推荐用短段落、编号步骤、伪代码和接口自己的局部字段表，避免把长流程写进单元格。简单接口不要硬拆无意义小节，复杂算法可直接紧跟伪代码。

增量项目的“代码入口与调用链”必须落到已核实模块及具体包、文件或相邻符号。新建类尚不存在时，写清目标模块、包和参照实现；不得只写仓库根目录、`src/` 或并不存在的模块名。接口内部逻辑还要说明每个响应字段从数据库列、计算、既有服务还是外部系统取得。

影响调用方的请求、响应和错误字段在该接口块内建立局部映射，不再重复 `contract_id`：

```text
direction | schema_path | page_field_or_caller | transform_validation | error_empty_behavior
```

不要写“查询相关数据”“处理业务逻辑”，也不要把简单 CRUD 强拆成重复的分层表。

#### 操作实现映射

执行明细中必须为当前故事每个 `OP-*` 保留一条操作实现映射。它不是固定章节，可以放在最适合的位置，但表头和字段语义必须可检索：

```text
operation_id | implementation_kind | ui_surface_refs | contract_ids | implementation_refs | decision_basis
```

- `implementation_kind` 使用 `frontend_only`、`http_api`、`async_task`、`external_integration`、`database_only`、`navigation` 或 `mixed`。
- `contract_ids` 写真实 OpenAPI `operationId`；无 HTTP 接口时写 `NONE` 并在 `decision_basis` 说明原因，不能用虚构的聚合接口占位。
- `ui_surface_refs` 引用阶段 3的逻辑载体；纯后台任务可写 `NONE`。
- `implementation_refs` 至少关联一个页面、接口、学习索引或任务的可检索标识。
- `decision_basis` 说明为什么该操作需要或不需要接口，以及复用、修改、新增的代码依据。

#### 条件：前端页面

仅当 `ui_required=true` 时出现。每个受影响页面、弹窗、抽屉或具有独立业务职责的嵌入区域必须成为一个独立、可定位的页面内容块，不能把多个页面的完整说明压进一张全局明细表。标题格式固定，层级可按当前文档选择：

```markdown
### 页面 [record-create] 创建记录
```

方括号中的 `surface_id` 在故事内唯一，并对应阶段 3的 `ui_surfaces`。页面索引表可以保留用于概览，但不能替代独立页面块。

页面完整性以阶段 3的 `ui_surfaces` 为需求范围基线：每个逻辑交互载体必须有且只有一个独立页面/弹窗/抽屉内容块，不得漏写或凭空扩展；阶段 4在块内补充真实的变更类型、页面类型、路由、代码入口和组件复用结论。

页面标题下先用简短元数据行提供稳定机器可检索信息：

```markdown
- 变更类型：modify
- 交互载体类型：page
- 页面类型：form
- 路由或入口：/records/new
- 开发前学习：PRD-01；FE-01
- 可复用组件：RecordForm（src/components/records/RecordForm.tsx）；ActionFooter
- 操作引用：OP-REQ-001-01
```

- `变更类型` 使用 `reuse`、`new`、`modify` 或 `delete`。
- `交互载体类型` 必须与阶段 3的 `ui_surface.surface_type` 一致；它是逻辑载体校验，不等同于前端路由。
- 页面元数据应列出本页面承载的 `operation_refs`；弹窗、抽屉和嵌入区域不得只作为一句布局描述隐藏。
- `页面类型` 可使用 `list`、`form`、`detail`、`dashboard`、`wizard`、`dialog`、`drawer`、组合类型或项目自定义类型；不要限制为三类。
- `开发前学习` 指向需要先学习的原型、前端代码、规范和依赖故事。
- `可复用组件` 写实际组件路径或符号及复用方式；没有现成组件时写明确的新建落点。

随后按页面实际类型自由组织，写清页面目标与入口、布局区域及顺序、数据来源、权限和真实业务状态。布局要具体到执行 AI 可以选择组件、划分区域和确定顺序；像素和断点仅在材料明确要求时写。状态只写实际存在的加载、空、失败、无权限、编辑、提交中、成功和冲突等情况。

PRD 已明确的路由、宽度、顺序、输入限制和触发方式直接采用，不改写为“以实施核验为准”。若动态菜单、前端规范或性能要求导致目标设计需要调整，写出证据和已确认决定。不要静默增加分页、长度限制、缓存、批量操作或额外按钮。

列表或组合页面包含列表时，在该页面块内写一行列表行为：

```text
pagination | page_size | default_sort | data_source | loading_empty_error
```

并逐列写局部表格：

```text
order | field | label | source_and_mapping | display_format | permission_and_empty | row_interaction
```

存在查询条件时在该页面块内逐项写：

```text
order | query_field | control | default_value | match_mode | options_source | validation | request_mapping
```

`match_mode` 明确精确、模糊、前缀、范围、多选或其他真实语义。没有查询条件时不生成查询表。

表单、编辑区或弹窗存在输入项时逐项写：

```text
order | area | field | component | source_and_mapping | default_display_edit | validation_and_linkage | error_and_permission
```

写清字段组件、数据来源、默认值、格式、显示/隐藏、只读/编辑、客户端和服务端校验、跨字段联动、错误文案或错误码、权限和脱敏。相同规则可分组，但不能用“其他字段同理”隐藏差异。

存在按钮、行操作、批量操作、菜单或自动动作时逐项写：

```text
action | location | visible_enabled_guard | confirmation | contract_id | request_mapping | success_behavior | failure_behavior
```

纯前端动作的 `contract_id` 使用 `FRONTEND:<name>`。必须区分可见、可用和执行前校验，并写清确认、防重复、成功刷新或跳转和失败回填。

存在用户交互或页面状态变化时，写关键流程：

```text
flow | trigger | steps_and_validation | success | failure_or_branch
```

以上字段、查询、操作和流程表都属于当前页面块，不再重复 `page_ref`。只写影响数据、状态、权限和验收的交互，不生成所有鼠标点击或通用状态全集。删除页面时重点写入口移除、调用方迁移和替代页面，不要求补写已删除页面的字段明细。

#### 条件：事件、任务和其他实现面

实际涉及时自由增加最合适的信息块：

- 事件或消息：生产者、消费者、schema、投递时机、去重和失败语义。
- 定时或批处理：触发方式、输入范围、分片或游标、重跑和失败恢复。
- 外部系统：调用方、凭证边界、超时、重试、限流和降级。
- 文件处理：格式、大小、存储、扫描、解析、失败和清理。
- 搜索索引：来源、mapping、同步、一致性和重建。
- 数据迁移：来源、目标、转换、校验、切换和回滚。

没有影响时完全省略，不把这些内容硬塞进 HTTP 接口或数据库章节。

#### 核心：AI 执行任务

必须包含：

```text
task_id | depends_on | files_or_symbols | change | related_refs | done_when | verification
```

- `task_id` 使用 `TASK-[故事ID]-NN`。
- `files_or_symbols` 来自学习索引，或已确认的新系统目录骨架。
- `change` 写清要改变的规则、契约和调用关系，不写“完成相关开发”。
- `related_refs` 至少关联 `learning_ref`，并按需关联 `REQ/AC`、页面和 `contract_id`。
- `done_when` 是可观察完成条件；`verification` 写可运行命令和预期结果。
- `files_or_symbols` 对增量项目必须确定所属模块和具体落点或相邻符号，不能只列仓库根目录或宽泛的 `src/`。
- `verification` 必须从当前仓库实际脚本或构建配置中核实；如果仓库尚无测试入口，明确新增哪个测试配置及先执行什么命令，不得杜撰命令。

任务粒度按依赖和验证边界决定，不按文件机械拆分。

#### 核心：验收映射

必须包含：

```text
acceptance_criterion_id | implementation_refs | test_case_ids | observable_result
```

每个 AC 关联页面或 `contract_id`、任务和 CSV 用例。测试覆盖正向及与实际风险相称的字段校验、操作校验、权限、失败、边界、幂等或并发场景；不为凑类别造用例。

阻塞、假设和风险只有在会改变实现、契约、验收或上线时才写。存在未解决阻塞时不得标记计划生成；没有时无需专设章节。

### 测试用例

文件：`[故事ID]-[用户故事名称]测试用例.csv`

固定表头：

```csv
case_id,story_id,acceptance_criterion_id,requirement_ref,implementation_refs,test_level,test_type,title,priority,preconditions,steps,test_data,expected_result,automation_candidate,environment,status
```

- `case_id` 使用 `TC-US-001-001` 格式。
- `implementation_refs` 用分号关联页面、字段、操作、`contract_id`、`learning_ref` 或 `TASK-*`。
- 每个 AC 至少有正向用例；失败、边界或安全用例按实际风险生成。
- `steps` 可重放，`test_data` 给出具体值或构造方式，`expected_result` 是外部可观察结果。
- `test_level` 和 `test_type` 使用真实类别，不强制生成 layout、interaction 等特定类型。
- `automation_candidate` 使用 `yes` 或 `no`；初始 `status` 使用 `not_run`。
- 用例预期只能断言本故事实现或已满足依赖能够观察到的结果。涉及其他页面、选择目录或服务时，必须关联其接口、任务或依赖故事。
- 页面点击、输入和弹窗流程使用 component/e2e 等合适层级；纯 API 用例只描述可通过接口观察的输入输出，不能夹带前端回滚或提示断言。

## 反向遗漏审计

生成后不要检查标题数量，而要从 PRD 和代码反向核对：

1. 每条 `REQ/AC` 是否能找到背景来源、实现位置和测试；AC 的实现语义是否与阶段 3 引用的 `OP-*` 一致，而不只是 ID 出现在文字中。
2. `prd_operation_catalog` 中每个 `covered` 操作是否都有唯一故事、逻辑交互载体（或无 UI 原因）、AC、操作实现决策、实施引用和测试引用；`excluded/deferred/blocked` 是否都有原因。
3. 每个受影响的页面和接口是否都有唯一独立标题块；每个表、事件、任务和外部系统是否都在明细中。
4. 每个列表的分页、排序、列和实际查询条件是否完整；新增分页、限制、默认值或排序是否有来源。
5. 每个表单字段、按钮和业务交互是否都有确定行为；交互每一步所需数据是否能在使用前取得。
6. 每个 `contract_id` 是否都有消费者、调用时机、代码链、业务逻辑、数据来源、失败语义和字段契约；页面所需字段、版本和预检查结果是否都存在。
7. 复用、新增、修改、删除的对象是否都有结论；删除项是否有迁移和替代方案。
8. 每项任务是否有真实模块、明确文件或符号、完成条件和已经核实可运行的验证方式，并引用相关 `OP-*`。
9. 数据库对象是否同时具备 DDL、数据产生/初始化方式、读写链路和回滚；字段命名与类型是否适配现有工程。
10. 增量接口是否适配当前项目的 URL 前缀、请求头、鉴权/租户上下文、响应包装、分页和错误模型。
11. 测试层级是否与步骤一致，是否错误断言了范围外故事的结果。
12. 删除重复契约、框架教程、泛化建议和空内容后，执行 AI 是否仍能直接开发，并且无需重新决定产品规则、业务数据来源或模块归属。

校验器只检查能可靠判断的文件结构、执行核心和引用关系。它不会证明接口时序可用、schema 字段齐全、SQL 数据来源闭合、复用结论真实、命令可运行或目标设计忠于 PRD。无法由脚本可靠判断的内容由直接开发语义核验和本次反向审计负责，不能用固定章节替代判断，也不能因为脚本返回 `VALID` 就跳过。

页面和接口属于可可靠校验项：严格比较 `operation_refs ↔ ui_surfaces ↔ 操作实现映射 ↔ OpenAPI x-operation-refs ↔ 页面/接口标题块`。任一侧缺少、多出、重复或关键标识不一致都必须失败。

## 完成与状态更新

只有以下条件全部满足才设置 `plan_generated=true`：

1. 三项文件存在，命名和路径与跟踪文件一致。
2. OpenAPI 可解析，实际存在的 operation 契约完整。
3. 直接开发语义核验结果为 `READY`：页面动作与接口时序、字段与数据来源、现有工程适配、代码落点和验证命令均已闭环。
4. CSV 可解析并覆盖每个 AC。
5. `REQ/AC → 页面或 contract_id → Task → Test` 可追溯。
6. 没有模糊占位、无来源扩项、“实施时再确认”的关键设计和未解决阻塞。
7. 以下命令成功：

```bash
python3 <skill-dir>/scripts/tracker.py validate <output-dir>/AI执行清单.json --check-artifacts
python3 <skill-dir>/scripts/tracker.py set <output-dir>/AI执行清单.json <story-id> \
  --field plan_generated --value true --check-artifacts
```

不得替用户设置 `development_completed` 或 `self_test_completed`。
