## 进入与退出条件

进入前必须存在：

- 已确认的 `AI执行计划物料清单.md`。
- 若阶段 2适用，已确认的 `系统技术选型清单.md`；若跳过，物料清单明确记录 `skipped_existing_stack`。

## 故事卡与命名

严格区分短标题与完整用户故事：

- `name` 是用于目录、文件名和看板扫描的短标题，使用“业务对象 + 用户动作或可观察结果”，例如“手机号验证码登录”“审批人驳回申请”。不要写“用户故事 1”“登录模块”“前端登录页”“开发登录接口”，也不要把完整三段式长句塞进 `name`。
- `user_story` 才是故事卡的完整业务表达。业务故事 `US-*` 使用：`作为 <具体角色>，我想要/希望 <业务行为>，以便 <明确价值>。`
- 角色具体到会影响权限、行为或价值的群体，例如“未登录访客”“订单审核员”“租户管理员”。不要无依据虚构画像，也不要只写“用户”“相关人员”。
- 行为使用业务语言说明用户想完成什么，不写 Controller、API、表、缓存、框架或部署方案。
- 价值回答为什么值得做，应是用户、运营、合规或业务可识别的结果，不写“完成需求”“实现功能”“提升体验”等空泛目的。

示例：

```text
name: 手机号验证码登录
user_story: 作为未登录访客，我想要通过手机号验证码登录，以便无需记住密码即可进入自己的账户。
```

确实没有直接用户角色、且无法归入业务故事的共享技术前置才使用 `TECH-*`。不要虚构“作为系统”；使用：`为了 <受益故事或业务能力>，需要 <技术前置>，从而 <解除风险或支持结果>。`，并在 `prd_refs`、依赖和范围中说明受益故事。

## 3C 与 INVEST 质量门

把 3C 落到本技能的实际流程：

- **Card**：`name`、`user_story`、范围和来源只保留简洁业务意图，不把阶段 4实施细节提前塞入故事卡。
- **Conversation**：在阶段 3对话中展示角色、价值、边界、拆分理由、依赖、假设、逻辑交互载体、业务接口能力和待决问题；重要结论进入范围、AC、风险或确认基线，不能只留在聊天隐含上下文。
- **Confirmation**：以 `acceptance_criteria`、确认后的操作/逻辑载体范围和 `catalog_confirmed_at` 固化“完成”的共同理解。确认前故事可协商；确认后如需改变范围，按基线漂移处理，不能静默改写。

每个候选故事逐项审查 INVEST：

- **Independent**：能够独立排序和验收；只保留真实契约、数据、行为或发布依赖。
- **Negotiable**：确认前保留方案协商空间，不把技术实现写成不可变需求；确认后实施包必须消除会改变契约的歧义。
- **Valuable**：`user_story` 明确受益角色和业务价值；只有技术前置可用 `TECH-*` 表达间接价值。
- **Estimable**：范围、AC、依赖和已知风险足以判断工作量；关键未知导致无法估算时阻塞，不假装可估算。
- **Small**：在团队约定的一个计划周期内可完成。没有团队容量时不虚构人天，只根据独立价值和复杂度信号继续拆分。
- **Testable**：每项价值都有具体、可观察的 AC，且不存在无法验证的形容词。

任何一项不满足时，先重写、拆分或标阻塞，再交给用户确认；不要生成一张形式上填满但不可实施的故事卡。

## PRD 操作台账与纵向切分规则

不要直接从 PRD 章节标题“凭感觉”生成故事。必须先逐页、逐流程、逐按钮建立 `prd_operation_catalog`，再把操作按独立业务价值组成用户故事。操作是用户在页面或流程中可执行、可观察的业务动作，不是数据库表、接口或前后端任务。

操作台账至少覆盖：查询、清空/重置查询、分页/排序（若 PRD 明确）、新增、查看详情、编辑、删除、批量操作、导入、导出、启用/停用、提交/审核/驳回/发布、重试/取消、上传/下载、弹窗确认以及 PRD 明确的其他按钮或自动触发行为。一个按钮包含多个业务动作时，按可独立验收的动作拆成多个操作；仅改变展示状态的控件可和所属主流程合并，但必须在操作名称或备注中记录。

每个 PRD 操作必须记录：

- 稳定 ID `OP-REQ-###-NN`（技术/架构操作使用 `OP-TECH-*` 或 `OP-ARCH-*`）。ID 不得包含故事 ID，故事拆分或合并时保持不变。
- 业务名称和 `operation_type`，推荐值为 `query/create/update/delete/business_action/batch/import/export/status_transition/async_task/external_call/other`。
- PRD 的 `REQ-###` 来源；必要时同时关联验收标准。
- 所属故事 `story_id` 和逻辑交互载体 `ui_surface_refs`。交互载体可以是页面、对话框、抽屉、阶段页、独立业务区域或外部页面；纯 API、自动任务等无 UI 操作可为空，但必须填写 `no_ui_reason`。
- `coverage_status` 只能是 `covered/excluded/deferred/blocked`；非 `covered` 必须填写原因，禁止静默遗漏。

每个需要用户确认的业务接口能力单独记录 `interface_capability_id`、业务能力名称、来源、服务的 `operation_refs` 和 `business_api_need`（`required`、`not_required` 或 `to_verify`）。它表示需求层需要的服务能力，不是 OpenAPI `operationId`，不包含 Method/Path、代码位置或复用/新增结论。

建立如下可反查链路，并在交给用户确认前逐项核对：

```text
PRD/原型按钮或自动行为 → REQ → Operation → Story → AC
                                  ↘ UI Surface / Interface Capability → Stage 4 技术设计/实施/测试
```

只要 PRD 中出现的按钮、操作或自动业务行为没有落到某个 `prd_operation_catalog` 项，目录就不完整。若确认不在本次范围内，必须保留该操作并标记 `excluded/deferred/blocked` 及原因，不能静默省略。

### CRUD 合并与独立拆分

单一业务对象、同一角色/权限域、同一页面上下文下的查询、新增、修改、删除，可以作为一个“信息维护”故事，并在该故事的 `operation_refs` 中分别列出 `query/create/update/delete` 操作；不要机械拆成四张卡。合并不得隐藏不同的校验、状态或副作用。

以下情形通常单独拆分故事：

- 审核、发布、授权、撤销、启停、归档、重试等改变状态或权限的动作。
- 批量、导入导出、异步任务、外部系统调用等有独立业务价值、错误语义或可回滚边界的动作。
- 不同角色、租户/数据域、审批链或安全边界。
- 主流程与高级流程可以独立交付和验收。

拆分依据必须是业务价值、规则、状态或可验收边界，而不是“这是前端/后端/数据库”或“这是一个接口”。在故事上填写 `story_split_rationale`；不要给单个操作写与归属矛盾的 `separate_story` 标记。如果一个动作只能和主流程一起交付，合并到主故事并保留为独立操作。

优先形成端到端可验证价值：

```text
角色触发 → 页面/API 输入 → 业务规则 → 持久化/外部副作用 → 可观察结果
```

按独立用户故事拆分，而不是照搬 PRD 模块标题或拆成“做表、后端、前端、联调”。这些横向工作应成为一个故事内的 AI 执行任务。

需要继续拆分的信号：

- 包含多个不同角色或多个可独立交付的业务价值。
- “以及”或“并且”连接的任一部分可以单独上线或验收。
- 验收标准跨越不同状态机、权限域或上下文边界。
- 需要大量互不相干的 API、页面或数据迁移。
- 关键依赖未确定，导致计划只能充满条件分支。

常见切分维度：

- 主流程与高级流程；首个可上线故事仍须包含安全的基本异常处理。
- 创建、查看、修改、关闭按业务价值拆分，不机械按 CRUD 拆分。
- 不同角色或权限域。
- 单条与批量、人工与自动、同步与异步。
- 本地能力与外部集成，以稳定契约连接。
- 平台或渠道只有在角色、交互、规则或可交付价值确实不同时才拆分；不要按单个 API 或技术层机械拆故事。
- 高风险迁移可成为 `TECH-###` 前置，但必须关联受益故事和验证结果。

纯技术条目只用于无法合理归入业务故事的共享前置、迁移或平台能力；不要用它恢复横向分层任务。

## 验收标准

每条验收标准必须：

- 描述外部可观察行为，不把具体实现当产品结果。
- 包含必要前置、触发、结果和错误语义。
- 明确角色、租户或数据域、状态和边界值。
- 使用稳定 `AC-[故事ID]-NN` 标识。
- 能映射到至少一个确定测试用例。
- 不使用“正常”“合理”“友好”“快速”等无口径词。

优先采用结构完整的 Given–When–Then：

```text
Given 未登录访客已输入有效手机号并取得未过期验证码
When 提交手机号和验证码
Then 系统建立该账户的登录会话并进入首页
```

一个 AC 只确认一个可观察结果或一组不可分割的结果。可使用等价的前置—触发—结果表述，但不能只写“支持登录”“保存成功”或把“完成前后端开发”当成验收标准。

每个故事写明角色、目标、价值、范围内、范围外、优先级、来源、风险和建议实施顺序。

## 依赖与共享所有权

只记录真实交付依赖，不把“同一模块”当依赖：

- 契约依赖：共享 schema 或 API 必须先稳定。
- 数据依赖：表、迁移或主数据必须先准备。
- 行为依赖：前序状态或能力必须存在。
- 发布依赖：部署或 feature flag 顺序约束。
- 外部依赖：第三方、权限或责任人决策。

规则：

- 依赖只能引用目录内稳定故事 ID，依赖图不得成环。
- 依赖故事排在使用者之前；真正可并行的故事不制造虚假顺序。
- 共享表、schema、组件或基础能力只能有一个所有者故事或 `TECH` 条目负责首次创建，其他故事引用稳定契约。
- 多个故事必须同批上线时仍保持各自验收边界，在发布依赖中声明原子发布组。

## 覆盖审计

建立：

```text
source/locator → REQ → Operation → Story → AC
                              ↘ UI Surface → Stage 4 技术设计
```

逐项检查：

- 每条有效 `REQ-###` 至少被一个故事覆盖。
- PRD、原型中确认属于本次范围的每个按钮、页面操作、自动触发或业务动作都至少有一个 `OP-*`；同一操作只能归属一个故事。
- 每个 `OP-*` 必须通过 `ui_surface_refs` 或明确的 `no_ui_reason` 连接到用户可见位置，并被至少一个带 `operation_refs` 的 AC 覆盖。
- `ui_surfaces`、故事 `operation_refs` 和 AC 的 `operation_refs` 必须互相可反查；交互载体不得成为未登记操作的孤立扩项。
- 单表 CRUD 的合并关系和非 CRUD 独立拆分理由必须能从故事级 `story_split_rationale` 与对话说明中复核。
- 每个故事有 PRD 来源，或有明确记录的技术必要性和受益故事。
- 重叠故事没有对同一能力给出互相竞争的所有权。
- 权限、加载、空状态、失败、取消、并发、审计、通知、导入导出、兼容、迁移和非功能要求已进入相应故事或明确不适用。
- 范围外事项被显式记录，没有在拆分中悄然丢失或扩张。

## 执行步骤

1. 重新读取已确认物料清单、有效 PRD 需求索引和已确认技术边界。
2. 从 PRD 逐页、逐流程、逐按钮建立 `prd_operation_catalog`。对查询、新增、修改、删除和其他操作分别登记，不因同属一个模块而合并遗漏；对明确排除项保留排除原因和状态。
3. 根据操作的角色、业务价值、规则、状态和验收边界组成候选故事；单表 CRUD 可合并，非 CRUD 动作按独立业务价值拆分，并给出故事级合并/拆分理由。
4. 为每个候选故事写短标题、完整三段式故事卡、`operation_refs`、AC、范围、依赖、风险和建议顺序。根据 PRD 和原型列出逻辑 `ui_surfaces`，每个载体引用相关操作；同时列出业务接口能力及其服务操作。此阶段不检索或设计具体路由、组件、接口地址、Method/Path、Controller 或数据表。
5. 执行双向覆盖审计：从每个 PRD 操作能找到唯一故事、逻辑交互载体和 AC；从每个故事、交互载体和 AC 又能追溯到 PRD 操作。检查空数组是否有真实依据，检查 CRUD 合并和非 CRUD 拆分是否合理。
6. 逐故事执行 3C/INVEST 审查；不满足时先重写、拆分或阻塞。
7. 生成 `AI执行清单确认.md`，以单个用户故事为连续审阅单元，把该故事的背景、来源、范围、页面/弹窗、按钮和操作、自动行为、业务接口能力、依赖、验收重点及待决问题放在一起；完整稳定 ID 追溯关系放到文末附录。初始 `confirmation_status: pending`。
8. 在对话中可按故事或按小批次请用户审阅；只有全部故事及跨故事问题完成确认，才把 MD 整体标为 confirmed。确认的是需求覆盖、故事边界、页面/按钮和业务接口能力，不是技术设计或固定章节模板。未确认不得生成正式 JSON。
9. 用户确认后更新 MD 的确认状态、时间、版本和确认内容，使用 `shasum -a 256 AI执行清单确认.md`（或等价 SHA-256 工具）计算其内容 hash，再派生 `AI执行清单.json`，三个完成状态初始均为 `false`，运行 `tracker.py validate`。
10. 下次调用先比较确认 MD hash；MD 修改后必须展示差异并重新确认，不能直接覆盖 JSON。

## AI 执行清单规范

### 先产出给用户确认的 Markdown

`AI执行清单确认.md` 是阶段 3 的第一份正式产物，面向产品负责人和研发负责人阅读，不是给下游 AI 直接执行的任务文件。它不采用强制固定章节名称，但必须采用“故事优先”的阅读组织：用户打开一个故事后，不需要跳到其他全局表格，就能确认这个故事为什么做、做哪些页面和操作、需要什么业务服务、依赖什么以及还有什么需要决定。

文档分成两个信息层级，名称和顺序可按项目调整：

1. **用户审阅主体**：按故事逐个展示业务内容。它是用户确认的主要界面。
2. **追溯附录**：保存生成 JSON 所需的完整稳定 ID 和关系。它服务于反查与派生，不抢占用户阅读主线。

用户审阅主体至少保证以下信息在同一个故事范围内连续出现：

- 完整故事卡、PRD/原型来源、范围内外、拆分或合并理由、依赖，以及与本故事直接相关的风险或待决问题。
- 本故事涉及的每个逻辑页面、弹窗、抽屉、阶段页或独立业务区域。每个载体独立命名，并在其下面列出用户能执行的按钮、查询、表单动作和可观察结果；不要只给一串 `UI-*` 引用。
- 不依附 UI 的自动回调、定时流转、异步处理或外部触发行为，单独列出，不能因为没有页面而遗漏。
- 本故事需要的业务服务能力，以及每项能力服务哪个页面动作或自动行为。这里只确认“需要什么业务服务”，不确认接口地址、HTTP 方法、OpenAPI operationId、代码位置或复用/新增结论。
- 对当前故事有区分度的验收重点、范围排除和待用户决定事项。通用于所有故事的工程常识不重复铺陈；完整 Given–When–Then 可在 JSON 和阶段 4继续细化。

用户阅读主体的表达约束：

- 不先放全量 `OP-* → UI-* → Story` 操作大表。可以有简短故事总览，但主体必须立即进入逐故事内容；全量操作关系移到文末追溯附录。
- 不在同一行或同一内容块合并 `US-004/005/007` 一类多个故事。共享页面或能力分别写入各故事，并通过依赖或共享说明关联。
- 不用超长表格单元格承载一整个故事或十几个操作。概览适合短表格；页面、按钮、自动行为、业务能力和决策适合短段落、标题或列表。
- `OP-*`、`UI-*`、`INT-*` 和 `business_action` 等机器标识只作为次要追溯信息，可放在条目末尾或附录；正文先使用产品和业务人员能直接理解的名称。
- 不输出逐故事重复的通用验收口号或完整 INVEST 打分。仅当某个故事存在拆分风险、不可估算、不可测试或其他异常时，展示对应结论和影响。
- 真正需要当前用户决定的问题放在文档开头汇总，并在受影响故事内重复定位；只会阻塞阶段 4联调、但不影响当前故事范围确认的问题单独标记为“后续输入”，不要与当前必答问题混在一起。

追溯附录必须足以派生 JSON，并与审阅主体一致，至少保留故事、`REQ-*`、`OP-*`、逻辑交互载体、业务接口能力及覆盖状态的稳定对应关系。附录可以使用紧凑表格或结构化块，但不得用它代替逐故事主体。用户修改主体内容后，必须同步更新附录、展示影响并重新确认；发现两者矛盾时不得生成 JSON。

- `name` 是简短业务标题，必须与 `file_stem` 中 ID 后的名称一致；不使用三段式长句、模块名或技术任务名。
- `US-*` 的 `user_story` 必须包含具体角色、业务行为和明确价值，符合“作为…，我想要/希望…，以便…”；`TECH-*` 使用“为了…，需要…，从而…”，不虚构用户角色。
- `priority` 只使用 `P0`、`P1`、`P2`、`P3`。
- `ui_required` 必须是布尔值：故事涉及新增或修改 Web、移动端、桌面端、小程序、表单、列表、弹窗或用户交互时为 `true`；纯 API、数据迁移或基础设施故事才可为 `false`，并保留判断依据。
- `prd_operation_catalog` 是全局唯一的 PRD 操作来源；每项使用不随故事拆分变化的 `OP-*`，记录精确来源定位、操作类型、故事归属、逻辑交互载体和 `coverage_status`。非 `covered` 必须有原因，无 UI 时必须填写 `no_ui_reason`。
- `interface_capability_catalog` 是需求层业务接口能力来源；每项使用稳定的 `INT-REQ-*`、`INT-ARCH-*` 或 `INT-TECH-*`，关联来源、故事和操作。它不等同于 OpenAPI 契约，不得填写 Method/Path、operationId、路由、代码路径或复用/新增/修改结论；这些留到阶段 4核验。
- 故事 `interface_capability_refs` 必须完整引用本故事的接口能力；纯页面展示且无服务需求的故事可以为空，但必须有可解释的依据。
- 故事 `operation_refs` 是本故事包含的操作清单，必须完整引用本故事 catalog 中所有 `covered` 操作；不要把故事 ID 编入操作 ID。`story_split_rationale` 只在故事级说明 CRUD 合并或独立拆分理由。
