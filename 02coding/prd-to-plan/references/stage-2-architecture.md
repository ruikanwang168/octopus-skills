# 阶段 2：本次需求技术框架与选型确认

只在确认本次需求需要沿用哪些技术、是否需要新增框架或基础能力时完整读取本文件。先读取 `core-rules.md`、`tracker-and-resume.md` 和已确认的 `AI执行计划物料清单.md`。

## 阶段目标与边界

阶段 2不是通用架构白皮书，也不是阶段 4的实施方案。它要回答：

```text
本次需求涉及哪些技术能力？
现有技术栈能否满足？
如果不能，缺少的是框架、普通依赖、中间件、基础设施还是业务代码？
确实需要新增时，应该引入什么，为什么，影响什么？
如果不需要新增，是否明确记录沿用现有技术栈？
```

不固定正文章节。只输出与本次需求和技术决策有关的信息，不为了填模板硬写完整架构、容量或非功能章节。

本阶段不承担以下工作：

- 不生成用户故事目录、页面/接口影响基线或单故事实施任务。
- 不把所有现有依赖逐项抄成技术清单；只分析本次需求相关的技术基线。
- 不因为存在理论上的高并发、微服务或事件驱动方案就主动引入复杂框架。
- 不把普通业务代码、配置调整或已有库的调用误写成新增框架。

## 进入与退出条件

进入前必须存在：

- 已确认的 `AI执行计划物料清单.md`；
- 已确认的项目类型和数据库基线状态；
- 阶段 1记录的 PRD、原型、前端、后端和数据库材料可访问，或缺口已经明确。

退出条件：

- 用户确认本次需求的技术沿用、新增或替换结论；
- 形成正式的 `系统技术选型清单.md`，包括“没有新增框架”时的明确结论；
- 物料清单的 `step_2` 更新为 `confirmed`。

如果技术结论会改变业务范围、接口契约、数据库兼容、部署边界、安全合规或后续故事拆分，未确认前标为阻塞，不生成正式选型清单。

## 按项目类型执行

### 全新项目

没有可继承的前端、后端、数据库或平台基线时：

1. 从已确认 PRD 提取产品形态、核心业务能力和实际技术约束。
2. 推荐需要的前端、后端、数据库、中间件、鉴权、文件、搜索、部署、测试和观测方案。
3. 至少提供一个真实可行的备选方案；所有方案基于同一组事实、假设和团队约束比较。
4. 给出推荐理由、适用边界、主要风险、成本和重新评估条件。
5. 用户确认后固化技术基线，供阶段 3和阶段 4引用。

### 增量项目

存在现有前端、后端或数据库基线时：

1. 从本次确认范围内的 PRD 提取新增或变更的功能点，不把整套历史系统重新做一遍架构选型。
2. 按功能点读取相关现有源码、工程规则、依赖声明、配置、数据库基线和测试入口，核实当前能力。
3. 对每个功能点判断它是由现有框架、现有库、配置、业务代码、新增普通依赖、新增框架、中间件、基础设施还是外部系统承载。
4. 明确现有技术栈能否满足；能满足时记录沿用依据，不强制提供替代架构。
5. 只有现有技术无法满足、引入可显著降低风险，或 PRD/合规/平台约束明确要求时，才提出新增框架或基础能力。
6. 对确需新增的能力只比较相关候选，说明集成边界、依赖方向、迁移/回滚、运维成本和后续故事影响。
7. 如果没有新增框架，必须明确写出：本次需求沿用已确认技术栈，不新增框架；普通依赖或业务代码变化另在阶段 4说明。

### 部分继承或混合项目

前端、后端、数据库或基础设施只有部分存在时，分别标记：

- 继承范围及证据；
- 缺失范围；
- 缺失范围是否需要完整选型；
- 新旧边界和集成验证方式。

不能因为存在任意一侧代码就跳过其他缺失范围的选型。

## 技术分类与判断规则

对每项技术变化先分类，再决定是否进入技术选型：

- **现有框架沿用**：当前工程已采用，且本次需求不改变其边界。
- **现有库或工具沿用**：已有依赖可以直接支持，不需要改变系统技术基线。
- **普通依赖新增**：只增加 SDK、组件、适配器或测试库，不改变系统主要架构；在选型清单中简要记录，详细版本和用法留到阶段 4。
- **业务代码或配置变更**：不属于新增框架，不要伪装成技术选型。
- **新增框架**：引入新的编程框架、应用框架、工作流/编排框架或会约束项目结构的核心技术。
- **新增中间件或基础设施**：消息队列、搜索集群、独立缓存、对象存储、任务平台等；说明它是否真的属于本次需求的必要能力。
- **外部系统或服务**：记录接口、凭证、网络和责任边界，不把外部系统名称直接当成内部框架。

新增技术必须回答：

```text
需求证据是什么？
现有能力为什么不够？
新增技术解决哪个具体问题？
不新增的替代方案是什么？
引入后影响哪些仓库、模块、数据、部署、运维和故事？
什么条件下应重新评估或移除？
```

## 分析方法

遵循以下推理链，深度应集中在本次需求相关范围：

```text
确认项目类型
→ 提取本次需求功能点和技术能力
→ 定位现有技术基线证据
→ 判断现有能力是否满足
→ 区分沿用/普通依赖/业务代码/新增框架/新增基础设施
→ 只对必要新增项比较方案
→ 形成沿用或新增结论
→ 用户确认
```

现有代码分析至少覆盖与本次需求直接相关的：

- 包管理和版本声明；
- 工程模块和目录边界；
- 路由、请求封装、服务入口或配置入口；
- 数据访问和数据库基线；
- 鉴权、租户、审计、任务、文件、消息或外部适配能力（仅在需求涉及时）；
- 构建、测试和部署入口（仅在选型会影响时）。

每个重要结论标明 `FACT`、`INFERENCE`、`ASSUMPTION`、`DECISION` 或 `OPEN`，并使用阶段 1的 `source_id + locator`。不能把依赖文件中出现某个包直接当作项目已经按该包的推荐模式实现。

## 用户确认策略

- 全新项目确认完整技术方案。
- 增量项目确认“沿用现有技术栈”或具体新增/替换项，不要求用户确认没有变化的每个既有依赖。
- 只增加普通依赖、配置或业务代码且不改变系统技术基线时，可以记录为实施事项，不把它升级为框架选型确认。
- 新增框架、中间件、基础设施、数据库技术、鉴权边界或部署方式必须单独说明并取得用户确认。
- 用户未确认时只能展示候选结论或 `.draft.md`，不得写 `confirmation_status: confirmed`。

## 技术选型清单规范（信息要求，非固定模板）

正式文件：`系统技术选型清单.md`  
可选草案：`系统技术选型清单.draft.md`

文件头保留：

```yaml
---
artifact: "technical-selection"
schema_version: "1.1"
confirmation_status: "pending"
baseline_id: "BL-YYYYMMDD-001"
decision_id: "ADR-001"
confirmed_at: null
---
```

当前 `schema_version` 使用 `1.1`。旧 `1.0` 清单是上一版偏通用架构报告的格式；再次调用时需要依据本文件重新分析本次需求并由用户确认，不能自动升级。

正文结构和章节顺序自由，但必须让下游 AI和用户获得：

- 项目类型、选型范围、已确认约束和明确的 PRD 来源；
- 与本次需求相关的功能点/技术能力及其分析依据；
- 现有前端、后端、数据库和平台技术基线，以及直接相关的源码定位；
- 每项功能点能否由现有技术栈支持；
- 如果不能，明确缺少的是业务代码、配置、普通依赖、框架、中间件、基础设施还是外部服务；
- 新增或替换技术的推荐方案、备选方案（仅在确有必要时）、不采用原因、集成边界、迁移/回滚和后续影响；
- 如果没有新增框架，明确写出“本次需求沿用现有技术栈，不新增框架”，并说明普通依赖、配置或业务代码变化留到哪个阶段；
- 未确认的约束、假设、风险和重新评估条件；
- 用户最终确认的沿用、新增或替换决定，以及确认时间和基线。

不适用的信息直接省略。不要为了满足固定章节而生成与本次需求无关的容量、微服务、消息队列、灾备或成本分析。

## 执行步骤

1. 读取阶段 1物料清单，确认项目类型、PRD、代码、数据库和工程规则的版本。
2. 从 PRD 提取本次需求相关的功能点和会影响技术决策的约束；不在此阶段拆用户故事。
3. 按功能点检索现有源码和工程配置，记录与结论直接相关的证据。
4. 建立“需求能力 → 现有技术支持 → 能力差距 → 技术分类 → 结论”的分析链。
5. 增量项目优先形成沿用结论；只对必要新增项进行局部方案比较。
6. 全新项目或缺失范围形成推荐和备选方案，并说明适用边界和成本风险。
7. 在对话中展示技术分析、沿用/新增决定、阻塞项和需要用户确认的内容。
8. 用户确认后生成正式清单，并将物料清单 `step_2` 更新为 `confirmed`。

## 完成检查

- 项目类型和选型范围有阶段 1依据。
- 分析围绕本次需求功能点，而不是泛化抄写整个现有系统。
- 现有源码和工程配置的关键结论有可检索定位。
- 每个相关功能点都有沿用、普通依赖、业务代码、新增框架、中间件、基础设施或外部服务的判断。
- 增量项目没有无依据引入新的框架或基础设施；没有新增框架时已经明确写出沿用结论。
- 全新项目提供了推荐方案和真实可行的备选方案。
- 所有新增或替换技术都说明原因、边界、影响、风险和重新评估条件。
- 没有把普通依赖、配置或业务代码变化夸大为框架选型。
- 未确认的技术决策没有写入正式确认文件。
- 用户已明确确认，正式清单与阶段 1基线一致。
