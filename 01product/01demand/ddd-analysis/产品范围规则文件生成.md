**PRODUCT_SPEC.md 要经过多轮范围裁剪和规则确认，再汇总生成。** 直接说“帮我写产品规格”，会把很多业务决策留给 AI 自行补齐。

下面给你一套 **10 步提示词**，按顺序发送。每一步看完结果、修正偏差，再进入下一步。

依据这份课程第 3—14 页整理，以下是可复用模板，包含为防止编造而补充的执行约束，并非全部逐字引用：

**1. 交代项目背景，让 AI 列功能全貌**

先提供真实条件。没有提供的信息，应当保留为待确认。

```plain
接下来我们要逐步完成 PRODUCT_SPEC.md。

项目背景：
- 项目名称：<填写>
- 产品定位：<为谁解决什么问题>
- 主要用户：<填写>
- 开发团队：<人数、能力与分工>
- 使用或部署环境：<填写>
- 现有系统及必须兼容的条件：<没有则说明>
- 时间与资源限制：<填写>
- 已明确必须做的内容：<填写>
- 已明确不做的内容：<填写>

本轮任务：
1. 复述你理解的项目目标与约束。
2. 按业务模块列出候选功能全貌，供后续裁剪。
3. 标出哪些内容来自我的明确输入，哪些只是你的建议。
4. 信息不足的地方列为“待确认”，不要自行补成事实。

本轮只分析，不写代码、不设计数据库、不创建正式规格文件。
```

你要检查：它是否理解了产品目的，有没有把“可能需要”写成“必须实现”。

课程原例是“简化版电商、单人开发、学习项目、本地部署”。**迁移到其他项目时，必须替换这些前提。**

---

**2. 定义核心任务，再做三问裁剪**

理论是：先确定用户怎样完成一次主要任务，再判断哪些功能必要。否则“没有它还能不能用”没有判断基准。

```plain
基于上一轮项目背景与候选功能，先整理核心用户任务：

- 谁发起？
- 要完成什么事情？
- 从哪里开始？
- 经历哪些关键步骤？
- 什么结果代表任务完成？

然后对每项候选功能执行三问裁剪：
1. 不做这个功能，系统还能完成核心流程吗？
2. 没有这个功能，用户还能完成主要任务吗？
3. 它解决的是当前真实问题，还是未来可能出现的问题？

输出表格：
功能｜删除后的影响｜三问分析｜建议保留/裁掉/待确认｜理由｜关联影响

最后分别列出：
- 建议纳入 MVP 的功能
- 明确建议不做的功能
- 必须由我决定的问题

注意：
- 不要把候选清单直接当成已确认范围。
- 不要遗漏保证业务正确性的机制。
- 不要只用“行业常见”“以后可能用到”作为保留理由。
```

课程例子：

+ 优惠券：没有它仍可购买，可以裁剪。
+ 库存扣减：删除会影响交易正确性，应保留。
+ 超时取消：若采用库存预占，不处理可能长期占用库存，应保留。

这里要看**删除后的后果**，不能只看功能大小。

---

**3. 人工修正裁剪结果，同时确认角色边界**

课程特别强调：AI 可以初筛，最终保留什么由你决定。

```plain
我对上一轮裁剪结果的决定如下：

保留：
- <功能及理由>

裁掉：
- <功能及理由>

调整：
- <原建议、调整结果及理由>

仍待确认：
- <问题>

请先更新功能范围，不要重新加入已裁掉的内容。

然后整理用户角色，逐个列出：
1. 这个角色要完成什么任务。
2. 可以执行哪些操作。
3. 本期明确不提供哪些能力。
4. 每项保留功能由谁触发。

检查：
- 是否有保留功能找不到操作角色？
- 是否给某个角色增加了未经确认的能力？
- 是否有角色能力与非目标清单冲突？

发现冲突先列出来，不要自行解决。
```

课程原例：管理员只管理商品和分类，不包含订单管理、用户管理、营销管理和报表。

要注意：课程后续又出现“发货”动作。因此实际生成规格时，**发货由谁触发、通过什么入口操作**应当列为待确认，不能擅自补出订单后台。

---

**4. 审查技术栈，保存选择理由**

这里的目标是解释每项组件的必要性。课程给出的技术栈也要重新审，不能直接照搬。

```plain
基于已确认的项目约束、MVP 功能和角色范围，分析技术方案。

如果项目已有技术栈，先检查能否满足需求，不默认替换。
如果需要新增组件，请逐项说明：

组件或方案｜解决哪项已确认需求｜现有替代方案｜
引入成本｜维护成本｜建议｜尚未验证的假设

重点检查：
1. 是否为未确认的未来需求引入组件？
2. 是否有能力重复的组件？
3. 是否存在更简单且满足当前要求的方案？
4. 哪些判断依赖实测，目前还没有证据？

对于关键选择，补充：
- 当前背景
- 备选方案
- 选择理由
- 重新评估的触发条件

不要编造性能、容量、并发量或实测结果。
本轮提供建议，等待我确认最终选型。
```

你随后用下面的格式收敛：

```plain
最终采用：<清单及理由>
本期不采用：<清单及理由>
重新评估条件：<条件>
尚未确定：<问题>

请将这些作为后续规格的技术决策依据。
```

例如，课程比较数据库全文检索与 Elasticsearch，关键经验是同时考虑检索需求、同步链路、一致性和维护成本。不能把“不用 ES”推广成所有项目的固定规则。

---

**5. 补齐关键业务规则和异常流程**

功能名称还不足以指导实现。这一步把“支持下单”“支持取消”等描述变成明确业务行为。

```plain
现在检查已确认功能中，哪些业务规则仍不明确。

逐项检查：
- 前置条件
- 操作权限
- 正常流程
- 重复操作
- 并发操作
- 失败后的处理
- 取消或超时
- 状态变化
- 数据是否需要保留历史快照

先列出待确认问题，并说明：
1. 不确定的具体是什么。
2. 不同答案会怎样影响行为。
3. 哪些问题会阻碍后续建模和实现。

不要替我决定业务规则。

对已经确认的部分，整理：
- 核心业务流程
- 状态及允许的流转
- 每条流转的触发者与条件
- 关键资源或库存的处理规则

本轮只确定业务语义，不生成表结构、SQL 或接口地址。
```

以课程电商为例，需要明确：

+ 同一 SKU 重复加购，是增加数量还是新增记录？
+ 什么时候预占库存？
+ 未支付超时怎样处理？
+ 哪些状态允许取消？
+ 已支付取消如何处理资金与库存？

最后一项在现有材料中没有完整方案，**应保留待确认，不能让 AI 按经验补成既定规则。**

---

**6. 把功能写成可验证的验收标准**

课程要求每项功能都有可判定标准。只写“支持购物车”“操作方便”无法验收。

```plain
将已经确认的 MVP 功能转换为可验证的验收条目。

按模块输出：
功能｜角色｜前置条件｜操作或触发｜
预期结果｜异常或边界情况｜验收方式

要求：
1. 每条验收对应已确认需求，不新增范围。
2. 将“支持、完善、方便、稳定”等模糊表达改为可检查行为。
3. 业务规则不明确时标记待确认，不自行填答案。
4. 正常流程之外，检查必要的重复、并发、失败和权限场景。

另外整理非功能需求：
- 性能与并发
- 数据一致性
- 安全
- 部署运行
- 接口或使用文档

区分：
- 已确认目标
- 建议目标
- 待测数据
- 已有实测结果

没有依据的响应时间、并发量、可用性指标，不要填写具体数字。
```

课程提供的合格例子是：

```plain
同一 SKU 重复加购只增加数量，不新增记录；
并发加购不出现重复购物车记录。
```

它比“支持加购”多出了可以验证的行为。不过具体数量上限、未登录行为等，仍需业务确认。

---

**7. 单独确认技术红线**

第八节红线是后续规则入口的输入，不能只写“注意安全”“代码规范”。

```plain
从已经确认的功能边界、业务规则和技术决策中，
提取需要写入 PRODUCT_SPEC.md 的技术约束红线。

每条列出：
约束内容｜依据哪项已确认决定｜适用范围｜如何检查

分为：
1. 本期禁止引入的能力或组件。
2. 必须遵守的数据和业务约束。
3. 必须满足的安全与变更要求。

要求：
- 不新增我没有确认的禁令。
- 不把课程项目选择当成所有项目的通用规则。
- 删除无法说明含义和检查方式的空泛表述。
- 发现约束相互冲突时先报告。
```

课程中的例子包括密码 BCrypt、迁移只追加不回改，以及不引入某些框架或组件。**这些要结合你的实际项目确认，不能整段原样搬走。**

---

**8. 汇总成 PRODUCT_SPEC.md 草稿**

到这一步才生成完整文档。以下八节结构直接依据课程整理。

```plain
现在基于前面已确认的决定，生成 PRODUCT_SPEC.md 草稿。

严格使用以下八节：

1. 项目概述
   名称、定位、目标用户、核心价值、现实约束。

2. 用户角色
   各角色的能力清单，以及本期明确不提供的能力。

3. MVP 功能清单
   按模块分组，每项包含可验证的验收标准。

4. 非目标清单
   不做什么、裁剪理由，以及对应三问中的哪一问。
   如果是外部限制或人工明确决定，也如实注明。

5. 核心业务流程
   主流程、关键异常流程、状态流转及关键资源处理规则。

6. 非功能需求
   已确认的性能、安全、一致性、运行和文档要求。
   明确目标与实测的区别。

7. 技术栈与裁剪理由
   采用什么、解决什么问题；
   不采用什么、为什么；
   哪些条件变化时重新评估。

8. 技术约束红线
   已确认的不引入什么、必须做什么及可检查约束。

生成要求：
- 只纳入已确认决定。
- 不重新加入已裁掉的功能或组件。
- 不新增数据库结构、接口地址、页面路由或代码方案。
- 同一概念、角色和状态使用统一名称。
- 尚未确认的信息，在相关章节明确标记“待确认”。
- 文末汇总待确认问题，不用猜测补齐。

先输出草稿供审查，不将它作为正式规格发布。
```

**这里有个顺序区别：**规格需要说明状态与库存的业务规则，后续 DOMAIN_MODEL.md 再展开字段、表结构与具体实现约束。不要在生成规格时提前让 AI 包办数据库设计。

---

**9. 执行课程要求的四查，再做一致性检查**

课程四查是：非目标完整性、验收可验证性、已裁组件回流、红线明确性。

```plain
审查上一轮 PRODUCT_SPEC.md 草稿，先报告问题，不直接修改。

执行四查：

一查 非目标是否完整
- 对照最初的候选功能清单。
- 每项是否都有保留、裁掉或待确认的去向？
- 已裁掉功能是否全部进入非目标清单并保留理由？

二查 验收是否可验证
- 逐条检查功能验收。
- 标出模糊、缺少预期结果或依赖未确认规则的条目。
- 给出改写建议，不擅自决定业务。

三查 技术栈是否回流
- 检查全文，包括流程和非功能需求。
- 是否重新出现已经裁掉的组件或架构？
- 是否出现没有理由的新增组件？

四查 红线是否明确
- 是否遗漏已确认约束？
- 是否存在口号式要求？
- 是否有相互矛盾的条款？

再补充检查：
- 角色权限与业务流程是否一致？
- 状态、触发者和取消规则是否一致？
- 是否存在编造的数字、性能结论或业务决定？
- 是否有示例被误写为本项目已确认需求？

输出：
位置｜问题｜原始依据｜影响｜修正建议｜是否需要我决定
```

你处理完问题后，再发送：

```plain
根据以下审查决定修订草稿：
<逐项填写接受的修改和明确的业务决定>

只修改涉及的问题，不扩大范围。
修订后列出剩余未决问题。
```

不要用“再检查一遍”作为唯一核验提示词。**明确检查对象和依据，才容易发现遗漏。**

---

**10. 保存正式文件，并重新读取验收**

这一步用于确认最终文件与讨论结果一致。

```plain
将已经审查确认的规格保存为项目根目录 PRODUCT_SPEC.md。
如果文件已经存在，先读取并保留无关内容，不直接覆盖已有决定。

保存后重新读取文件，逐项核对：

1. 做什么：按模块列明。
2. 不做什么：有明确理由和裁剪依据。
3. 验收：每项功能有可验证标准。
4. 角色：能力与不提供的能力明确。
5. 技术栈：每项有理由。
6. 裁掉组件：有理由，必要时有重评条件。
7. 技术红线：已确认约束完整。
8. 核心流程：关键步骤、状态与资源规则自洽。

每项输出：
通过/不通过/待确认｜文件中的具体位置｜依据

最后报告：
- 实际保存路径
- 尚未解决的问题
- 哪些未决问题会阻碍领域建模或实现

未解决的项目不要标记为通过。
```

正式进入下一阶段时，还可以在新会话发送：

```plain
读取项目根目录 PRODUCT_SPEC.md。

先不要设计数据库或写代码。
请依据文件回答：
1. 产品服务谁，解决什么任务？
2. 本期做什么、不做什么？
3. 各角色能做什么？
4. 核心流程与关键规则是什么？
5. 技术栈和红线是什么？
6. 还有哪些待确认问题？

每项引用文件中的具体章节或条目。
```

这能检查新会话是否读到了正确规格；**复述正确之后，仍需在后续实现中检查是否遵守。**

你实际需要准备的输入是：**项目背景、业务材料、现实约束，以及每轮需要你决定的问题。** 其余清单、草稿和审查可以让 AI 协助完成，但不能跳过你的业务判断。
