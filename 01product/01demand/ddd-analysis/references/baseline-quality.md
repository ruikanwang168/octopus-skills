# 业务基线的内容完整性与质量

形成、审阅或更新基线时读取。按新建与增量检查内容是否足够支撑产品设计、业务确认和开发讨论。标题、顺序、表格与篇幅可以变化，必需业务信息不能被“简洁”裁掉。

## 新建项目：建立可接手的业务全貌

| 内容 | 应说清什么 | 不足的表现 |
|---|---|---|
| 背景与定位 | 为什么发起、业务环境与当前做法、服务什么业务范围 | 直接从一条规则或功能开始，接手者不知项目做什么 |
| 业务目标 | 期望改变的业务结果、判断是否达成的方式 | 只有“提升效率”等口号，或把上线本身当业务结果 |
| 干系人 | 已知使用者、处理/维护者及相关责任方，他们的诉求、职责和交接 | 只有笼统“用户”，或凭常识补管理员、领导等角色 |
| 业务痛点或机会 | 谁在何种场景遇到什么障碍及影响；新机会有哪些待验证假设 | 将“没有系统/没有按钮”直接当根因，或虚构历史事故 |
| 业务解决方案 | 采用什么机制、为何适合、如何改变现有做法，主流程和异常如何完成 | 用功能列表代替方案，或跳到框架、接口与数据库 |
| 模块划分 | 按业务能力说明模块职责、核心功能、协作关系和本期范围 | 只有模块名，或按页面、前后端目录、通用菜单凑模块 |
| 核心用户故事 | 主要角色在具体情境下完成什么、获得什么价值，归属哪个模块及如何验收 | 只有操作点，没有价值、规则、验收或核心链路覆盖 |
| 范围与约束 | 本期包含/排除及理由、相关业务约束、关键来源与待确认影响 | 没有交付边界，或将未知内容写成不适用 |

小工具同样需要这组内容，可以合并表达：一段背景与目标、一个明确的业务模块、一条覆盖主任务的故事及验收即可。规模小决定详略，不意味着它只交输入输出规则，也不要求为它编出多个模块或组织角色。

尚无历史的新业务，用机会和待验证假设替代不存在的历史痛点，不能因此省掉背景、目标、干系人、方案和故事。

## 增量迭代：让人看清系统如何升级

| 内容 | 应说清什么 | 不足的表现 |
|---|---|---|
| 相关系统现状 | 业务定位、相关干系人、现有模块能力、主流程、现行规则及证据覆盖范围 | 只有几个函数的行为，没有业务链路和模块上下文 |
| 迭代背景与目标 | 当前问题在哪里、为什么升级、希望改变什么业务结果 | 只写“增加某功能”，没有必要性与目标 |
| 升级功能与方案 | 哪些模块新增、修改、废弃或保留什么；原来如何、本次如何、原因是什么 | 只写未来规则，读不出相对现状的变化 |
| 升级故事与验收 | 受影响角色需要完成的任务、业务价值、变化规则及可观察验收 | 只有代码差异，或遗漏原有行为的保留要求 |
| 影响范围 | 相关模块、人员、流程、规则、数据和交接如何受影响；有信号才展开历史、在途、报表、通知等 | 没查就说“不受影响”，或把业务规则保留等同于无改造影响 |
| 生效与兼容边界 | 新旧规则对哪些业务事项适用、在途如何处理、历史是否回写、关键失败谁接手 | 将历史不回写误解为旧在途也不适用新规则 |
| 本期范围与决策状态 | 本次交付及排除内容、已确认与待确认、依据冲突和影响 | 把局部迭代写成全系统重做，或把目标写成已实现 |

只梳理足以解释本次迭代的现有系统范围，不要求重写全量历史需求。代码证据紧邻关键现状和影响判断，不让调用链占据业务正文。

## 模块与用户故事的质量

模块按业务职责组织，每个核心模块都应有实际能力和所服务的故事。按需说明模块间交接；模块不直接等于限界上下文或技术服务。

每条核心故事分清短标题、完整描述和规则/验收，可以用短文或表格呈现，不要求每条都复制一张表：

- **短标题**：优先采用“角色＋业务动作＋必要对象/条件”，方便定位，例如“申请人撤销未领取的借用”；不只写“撤销管理”，也不将整段描述塞成标题。
- **完整描述**：优先采用“作为〈角色〉，在〈具体业务场景〉下，我希望〈业务行为〉，以便〈业务价值〉”。句式可以调整，角色、场景、行为、价值四项要清楚。
- **规则与验收**：独立说明前提、成功、拒绝和适用的失败结果；不要把所有分支挤进故事描述。

完整内容应能找到以下信息：

- 谁在什么业务情境下需要完成什么任务；
- 任务解决的痛点或目标，以及业务价值；
- 所属模块、必要前提、主要行为和可观察结果；
- 影响完成判断的关键规则、拒绝/失败边界和业务验收。

例如标题“申请人撤销未领取的借用”，描述“作为借用申请人，在申请已批准且尚未领取器材、也不再需要本次借用时，我希望撤销申请，以便释放不再需要的器材时段”。再由已确认规则补足资格、成功标准和失败去向。

场景应说明业务触发或所处阶段，避免“在使用系统时”等空泛条件。价值应回应痛点、角色目标或必要约束，避免“以便完成撤销”等对动作的重复，以及“提升体验”等无法对应当前问题的口号。材料没有说明业务价值时，定向澄清或标为待补充，不为了凑齐句式编造理由。

核心故事应覆盖本期从发起到结果的业务链路，既包括主要使用者，也包括真正承担处理职责的参与者。支撑能力关联它服务的故事；不虚构“作为系统”或“作为管理员”来填满列表。不将每个校验分支、按钮、弹窗或技术任务单独包装成故事。

## 明确、精准、易读

- **明确**：关键规则说清参与者、对象、前提、允许/拒绝行为及结果。含糊的“自动”“完成”“及时”等要落实为可观察业务含义。
- **精准**：每个模块和核心故事能关联问题、目标或必要业务约束。区分历史约定、当前实现、本次目标；来源范围未知的内容不标为已核实。
- **易读**：先帮助读者建立项目或迭代全貌，再下钻模块、故事与规则。使用业务语言，同一事实只完整表述一次；过程记录与技术检索细节不挤占正文。
- 数字应有来源或属于业务方明确决定。未知值用验证方法或待确认表达，不编造成效或规模指标。
- 术语、状态、数据可见性、外部依赖、时效或审计等专项内容按业务信号补充，不为了完整率补无关章节。
- 不以固定章节、字数、表格数或故事数量衡量质量；有标题却没有实际业务信息，同样不合格。

## 交付前复核

1. 找一个未参与访谈的读者视角：能否理解项目背景、目标、服务对象、业务问题与总体方案？增量能否理解原系统与升级动机？
2. 能否从业务目标/痛点追到方案、模块和核心故事，且故事覆盖主要角色及本期主流程？有没有孤立模块或只含功能名的故事？
3. 每条核心故事的短标题是否可定位角色任务，描述是否包含具体场景、行为与有依据的价值？是否能判断完成、拒绝和适用的失败结果？验收是否检验业务结果，而不是仅检验按钮存在或请求提交？
4. 增量能否对照三类材料或明确不适用项，看出每项变化前后差异、相关保留行为、影响与兼容边界？
5. 是否存在超出证据的“已支持”“不受影响”“已确认”，以及没有依据的角色、痛点、模块或数字？
6. 文档状态是否与确认程度一致？缺口是否标出影响、所需事实或决定？职责虽已指定，但异常如何交到责任方是否仍不清楚？

发现核心内容缺失时补充分析、读取相关材料或定向澄清。暂时无法补齐则交付标明缺口的草案，不用空标题、泛化用户故事或“以后完善”冒充完整基线。核心结论确认、非阻塞缺口影响被用户接受后，才标为已确认基线。
