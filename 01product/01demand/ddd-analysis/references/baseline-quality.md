# 业务基线的内容完整性与质量

形成、审阅或更新基线时读取。按新建与增量检查内容是否足够支撑产品设计、业务确认和开发讨论。标题、顺序、表格与篇幅可以变化，必需业务信息不能被“简洁”裁掉。

## 完整表达与去重的边界

- **先保证完整，再消除复述**：原始诉求、已定决策、必要规则与交付边界均应在正文中有明确说明。去重时将信息归到合适位置，不能只保留标题、关键词、原文链接或“支持某能力”就视为覆盖。
- **按业务含义判断重复**：只有事实、用途、适用条件和结果均相同，且没有新增信息的表述才合并。不同角色、不同场景、不同约束或不同失败结果，即使用词接近也须保留；同一职责不等于同一任务。
- **区分必要呼应与复述**：目标解释预期改变，方案解释如何实现，故事说明角色任务，规则限定允许条件，验收说明如何判断正确。它们可以涉及同一能力，不能因关键词重复就删去其中一层。
- **细节保留到能够判断结果**：按实际业务信号写清关键参与者、对象、前提、行为及成功、拒绝或异常结果。规则可以集中引用，但故事仍需有自身的可观察结果；流程图、表格和摘要不能替代关键条件、交接与例外。
- **未知须有明确缺口**：必要信息不足时说明缺什么、影响什么、需要什么事实或决定，继续完成其他已知内容；不能默默略去，也不编造内容填满。未决标记不代替已有部分的具体分析。

## 新建项目：建立可接手的业务全貌

| 内容 | 应说清什么 | 不足的表现 |
|---|---|---|
| 背景与定位 | 为什么发起、业务环境与当前做法、服务什么业务范围 | 直接从一条规则或功能开始，接手者不知项目做什么 |
| 业务目标 | 期望改变的业务结果、判断是否达成的方式 | 只有“提升效率”等口号，或把上线本身当业务结果 |
| 干系人与角色诉求 | 已知使用者、处理/维护者及相关责任方的职责，以及各自在具体场景中的痛点或目标、对应解决思路与预期变化 | 只有角色名单，没有诉求与方案对应，或凭常识补角色和痛点 |
| 业务痛点或机会 | 谁在何种场景遇到什么障碍及影响；新机会有哪些待验证假设 | 将“没有系统/没有按钮”直接当根因，或虚构历史事故 |
| 业务解决方案 | 采用什么机制、为何适合、如何改变现有做法，主流程和异常如何完成 | 用功能列表代替方案，或跳到框架、接口与数据库 |
| 模块划分 | 按业务能力说明模块职责、核心功能、协作关系和本期范围 | 只有模块名，或按页面、前后端目录、通用菜单凑模块 |
| 核心用户故事 | 主要角色在具体情境下完成什么、获得什么价值，归属哪个模块及如何验收 | 只有操作点，没有价值、规则、验收或核心链路覆盖 |
| 范围与约束 | 本期包含/排除及理由、相关业务约束、关键来源与待确认影响 | 没有交付边界，或将未知内容写成不适用 |

小工具同样需要这组内容，可以合并表达。确实只有一个业务职责和一条完整任务时，可以用一个模块、一条故事及其验收；实际有多个独立任务或不同责任方时，仍按业务展开。规模小不等于只交输入输出规则，也不要求编造额外模块或角色。

尚无历史的新业务，用机会和待验证假设替代不存在的历史痛点，不能因此省掉背景、目标、干系人、方案和故事。

## 角色痛点分析与方案对应：两种场景共用

对主要使用者、实际处理/维护者及其他受影响角色，建立“角色 → 场景 → 痛点或目标 → 业务影响 → 解决思路与预期变化 → 模块/故事”的可读对应关系。可以使用局部表格或短文，也可以与干系人说明合并；已说明的痛点和方案引用即可，不再逐处完整复述。

痛点分析应让读者直接找到“谁在什么任务中受什么阻碍、为何受阻（已知则说明）、会有什么后果、方案怎样改变它”。合并章节不等于省略这层分析；只有“访客想了解流程”“维护者想更新内容”是任务目标，不能算已经分析了痛点。

区分已确认痛点、分析假设和已知职责。原始诉求能支持推断时，可以写明“待验证痛点假设”、推断依据及需要核实的关键问题；不能因没有访谈数据就停止分析，也不能把可能后果写成已发生事故。没有合理推断依据时保留职责目标或业务机会，不为每个角色强凑痛点。分析阻碍而非简单把功能反写成“没有某按钮/模块”。

- 每个主要角色应有已知诉求或职责目标，不要求人人都有痛点。痛点未核实就标为待核实，不能从“负责审核/维护”直接推断其工作低效。
- 同一角色在不同场景中可能有不同问题；不同角色也可能共同受一个问题影响。保留这些差异，不统一改写成“效率低、体验差”。
- 解决思路说明业务如何改变以及该角色预期获得什么结果，并能追溯到模块或故事；不以“增加某模块”代替解决逻辑。
- 一个整体方案可以回应多个角色，不按角色硬拆模块；某项诉求本期不解决或采用人工替代时，说明取舍和影响，不自动扩大范围。
- 核对角色之间的诉求冲突，以及便利一方是否给另一方增加操作、维护、等待或风险成本；说明由谁承担及是否接受。
- 增量只针对本次变化涉及的角色建立或更新对应关系，区分原有问题、期望改善和新增负担。

## 增量迭代：让人看清系统如何升级

| 内容 | 应说清什么 | 不足的表现 |
|---|---|---|
| 相关系统现状 | 业务定位、相关干系人、现有模块能力、主流程、现行规则及证据覆盖范围 | 只有几个函数的行为，没有业务链路和模块上下文 |
| 迭代背景与目标 | 当前问题在哪里、为什么升级、希望改变什么业务结果 | 只写“增加某功能”，没有必要性与目标 |
| 升级功能与方案 | 哪些模块新增、修改、废弃或保留什么；原来如何、本次如何、原因是什么 | 只写未来规则，读不出相对现状的变化 |
| 升级故事与验收 | 受影响角色需要完成的任务、业务价值、变化规则及可观察验收 | 只有代码差异，或遗漏原有行为的保留要求 |
| 影响范围 | 相关模块、人员、流程、规则、数据和交接如何受影响；有信号才展开历史、在途、报表、通知等 | 没查就说“不受影响”，或把业务规则保留等同于无改造影响 |
| 生效与兼容边界 | 新旧规则对哪些业务事项适用、在途如何处理、历史是否回写、关键失败谁接手 | 将历史不回写误解为旧在途也不适用新规则 |
| 本期范围与决策状态 | 本次交付及排除内容、已确认与待确认、依据冲突和影响 | 把局部迭代写成全系统重做，或把目标写成已实现 |

只梳理足以解释本次迭代的现有系统范围，不要求重写全量历史需求。代码证据紧邻关键现状和影响判断，不让调用链占据业务正文。

## 模块与用户故事的质量

模块按业务职责组织，每个核心模块都应有实际能力和所服务的故事。按需说明模块间交接；模块不直接等于限界上下文或技术服务。

每条核心故事分清短标题、完整描述和规则/验收，可以用短文或表格呈现，不要求每条都复制一张表：

- **短标题**：优先采用“角色＋业务动作＋必要对象/条件”，方便定位，例如“申请人撤销未领取的借用”；不只写“撤销管理”，也不将整段描述塞成标题。
- **完整描述**：优先采用“作为〈角色〉，在〈具体业务场景〉下，我希望〈业务行为〉，以便〈业务价值〉”。句式可以调整，角色、场景、行为、价值四项要清楚。
- **规则与验收**：独立说明前提、成功、拒绝和适用的失败结果；不要把所有分支挤进故事描述。

完整内容应能找到以下信息：

- 谁在什么业务情境下需要完成什么任务；
- 任务解决的痛点或目标，以及业务价值；
- 所属模块、必要前提、主要行为和可观察结果；
- 影响完成判断的关键规则、拒绝/失败边界和业务验收。

例如标题“申请人撤销未领取的借用”，描述“作为借用申请人，在申请已批准且尚未领取器材、也不再需要本次借用时，我希望撤销申请，以便释放不再需要的器材时段”。再由已确认规则补足资格、成功标准和失败去向。

场景应说明业务触发或所处阶段，避免“在使用系统时”等空泛条件。价值应回应痛点、角色目标或必要约束，避免“以便完成撤销”等对动作的重复，以及“提升体验”等无法对应当前问题的口号。材料没有说明业务价值时，定向澄清或标为待补充，不为了凑齐句式编造理由。

核心故事应覆盖本期从发起到结果的业务链路，既包括主要使用者，也包括真正承担处理职责的参与者。支撑能力关联它服务的故事；不虚构“作为系统”或“作为管理员”来填满列表。不将每个校验分支、按钮、弹窗或技术任务单独包装成故事。

按独立业务目标拆故事。同一角色在同一任务中阅读说明、查看示例和获取模板，通常可以作为一条准备任务的组成部分；只有触发场景、价值或交付边界确实独立时才拆开。不要为凑固定故事数量拆碎，也不要为缩短文档合并不同角色或独立业务目标。

反向检查过度合并：如果一条“维护者更新内容”同时包含结构调整、知识编写和对外生效，而这些任务可以分别发起、完成或验收，应拆清独立目标及交接。只在业务已有相应决定时展开发布、审核等职责，不因为拆故事额外增加机制。

验收须能给出前提、操作和预期结果。“可以查看”“条件可辨认”“有可发现的核对结果”若不能据此判断对错，仍不够具体；可以用明确标为示例的代表场景检验机制，不等完整运营内容清单齐备才分析功能。外部资源区分本站提供访问入口、上线前人工核对和第三方持续可用性，不将后者默认写成本站保证。

## 缺口如何收敛

- **关键业务决定**：不同答案会改变范围、责任、规则或完成条件，例如谁能决定内容生效、缺少关键材料能否受理。给出当前依据、候选方案、建议理由及取舍，再请求必要裁决；未获决定时明确受影响部分，其他已知业务继续展开。
- **交付准备项**：具体负责人姓名、运营内容填充、测量基线等，只有实际改变业务机制或本期交付承诺时才作为关键缺口。说明由谁以什么产物补齐即可，不因没有量化指标、正式用户研究或全部实例而暂停整个需求分析。
- **内容也是交付物时**：先明确首期是否承诺内容交付；缺少完整清单影响规模和内容验收，但不妨碍梳理已有机制。可提出候选清单或代表路径供评审，标明建议，不声称它已被确认。
- 同一缺口在一处说清所需决定与影响，相关规则和故事只提示其适用限制，不反复重写问题。草案允许未决，但已有部分仍要具体，不能用“待确认”代替职责分析、方案比较或验收设计。

## 展示形式与内容归位

以下是各类内容的默认表达及选择条件，不是固定章节模板，也不要求照抄列名。用户指定形式优先；少量信息可用短文或列表合并，多项对应与前后差异优先用表格，先后关系和分支用流程表达。一项信息选择一个主要位置完整说明，其他位置只保留必要概述或引用。

| 内容 | 默认展示形式及调整条件 | 内容边界与去重 |
|---|---|---|
| 背景与定位 | 短段落；说明发起缘由、业务环境与服务范围。 | 不把功能、规则和未决问题全部塞入背景。 |
| 业务目标 | 简单目标用列表；多个目标需对应达成方式时，用“目标—预期结果—判断方式”表。 | 不编造成效指标，也不把全部故事验收再列一遍。 |
| 角色与痛点分析 | 默认用对应表，说明角色/场景、痛点或职责目标、影响、方案及关联故事；只有单一简单场景时可用明确标识的短文。 | 就近区分事实与假设；与干系人说明合并，避免另建重复的痛点表和方案表。 |
| 业务方案与流程 | 短文解释机制，简单顺序用步骤或箭头；存在条件分支、返回或多角色交接时优先用流程图，宿主支持时可用 Mermaid。 | 图表达流转，文字补关键条件、责任与例外；图文各有作用时保留，不再复制一份没有新增信息的完整流程。 |
| 模块与能力 | 默认用模块职责表，说明负责的能力、协作及关联故事；单模块小工具可用条目。 | 不逐条复述规则，不在“本期纳入”重新抄模块功能。 |
| 关键业务规则 | 编号列表；多个条件决定不同结果时用局部决策表。 | 跨故事规则集中定义，单故事规则就近说明；每条相关故事保留适用前提及预期结果，避免复制规则全文。 |
| 用户故事与验收 | 每条以短标题、完整故事描述和验收列表展开；故事多时可增加简短索引表。 | 已纳入的独立任务及关键成功、拒绝或失败场景须有描述与验收。索引不代替正文；规则引用不代替结果说明；整体验收补跨故事组合。 |
| 增量现状与升级 | 默认用前后对照表，结合模块写原行为、本次变化及必要来源；有材料冲突时在对应项说明。 | 合并现状、差异、升级与证据，变化类型仅标实际涉及项，不为凑齐四类编造变化。 |
| 影响与兼容 | 少量影响用列表；多个对象需对应处理方式时用影响表。 | 只写连带后果、存量、新旧生效及职责变化，不重复功能表或填写无信号的全系统清单。 |
| 范围、未决与来源 | 范围用纳入/排除列表；多项未决用“所需决定—影响—候选方案”表；状态和总体来源简短说明。 | 模块引用必须足以分清本期与后续范围；决定就近归位，必要来源紧邻结论，不另附完整访谈、检索过程或重复免责声明。 |

展示形式服务于理解：单元格若需要塞进多个独立段落，应拆分维度、缩小表格或改用条目；不为采用表格补空列、虚构字段或凑数量。形式调整后仍须让背景、目标、痛点、方案和故事可分别定位。

去重按本文件开头的业务含义判断，不追求字面零重复或统一压缩比例。必要防护写明对应风险，尚未采纳的扩展建议不混入本期；排除项只用于消除当前诉求相邻的真实歧义。

## 明确、精准、易读

- **明确**：关键规则说清参与者、对象、前提、允许/拒绝行为及结果。含糊的“自动”“完成”“及时”等要落实为可观察业务含义。
- **精准**：每个模块和核心故事能关联问题、目标或必要业务约束。区分历史约定、当前实现、本次目标；来源范围未知的内容不标为已核实。
- **易读**：先帮助读者建立项目或迭代全貌，再下钻模块、故事与规则。遵循上面的内容归位规则；面向业务读者，不把 DDD 方法解释、检索过程或测试报告写成产品要求。
- 数字应有来源或属于业务方明确决定。未知值用验证方法或待确认表达，不编造成效或规模指标。
- 术语、状态、数据可见性、外部依赖、时效或审计等专项内容按业务信号补充，不为了完整率补无关章节。
- 不以固定章节、字数、表格数或故事数量衡量质量；有标题却没有实际业务信息，同样不合格。

## 交付前复核

1. 找一个未参与访谈的读者视角：能否理解项目背景、目标、服务对象、业务问题与总体方案？增量能否理解原系统与升级动机？
2. 是否能直接定位主要角色的痛点分析，而不是只有角色名单、想做的动作或一句“困难待验证”？障碍、影响和解决思路是否对应，事实与假设是否区分并有依据？角色间冲突及新增负担是否处理？故事是否覆盖本期主流程，有没有孤立模块或只含功能名的故事？
3. 每条核心故事的短标题是否可定位角色任务，描述是否包含具体场景、行为与有依据的价值？原始诉求和已定决策是否都能找到负责的能力与验证位置？是否能判断完成、拒绝和适用的失败结果？验收是否检验业务结果，而不是仅检验按钮存在或请求提交？
4. 增量能否对照三类材料或明确不适用项，看出每项变化前后差异、相关保留行为、影响与兼容边界？
5. 是否存在超出证据的“已支持”“不受影响”“已确认”，以及没有依据的角色、痛点、模块或数字？
6. 文档状态是否与确认程度一致？缺口是否标出影响、所需事实或决定？职责虽已指定，但异常如何交到责任方是否仍不清楚？
7. 先逐项核对原始诉求与已定决策的说明、取舍或缺口，以及已纳入任务和关键规则的验证位置，再检查展示及重复。每次删改是否丢失角色差异、适用条件、例外、结果、必要来源或验收？表格和图是否保留必要解释，是否只是把应说明的信息变成索引或“详见”？不得以字数减少作为通过依据。
8. 是否把可独立发起和验收的不同职责塞进一条泛化故事，或用“等待全部清单/指标”掩盖可继续完成的分析？未决项是否给出必要的候选方案和影响，而不是只留下问题？

发现核心内容缺失时补充分析、读取相关材料或定向澄清。暂时无法补齐则交付标明缺口的草案，不用空标题、泛化用户故事或“以后完善”冒充完整基线。核心结论确认、非阻塞缺口影响被用户接受后，才标为已确认基线。
