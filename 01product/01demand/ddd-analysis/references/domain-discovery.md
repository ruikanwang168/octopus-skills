# 用 DDD 视角发现业务规则

本参考用于业务澄清，提供选题依据，不是必问清单。只对会改变本次业务判断的疑点提问，已经清楚的内容直接使用。

## 从一个具体场景开始

先建立项目背景与业务全景：为什么发起、为谁服务、有哪些相关责任方、当前如何完成任务、希望改变什么结果。把“要一个功能”还原成具体场景里的障碍、业务后果和目标，再问现有能力或更小变化能否解决。

新项目先理解背景、目标和干系人，再形成方案与能力地图；增量先了解相关现有系统及主流程，再找升级点。不要一开始就沉入状态、异常或局部功能，把整体业务遗漏。

例如用户说“要自动审批”，优先确认哪些申请可直接通过、谁承担误批后果、哪些情况必须人工决定；不要先问审批页如何布局。

尚无历史使用的新产品，检验预期场景和关键假设，不要求用户捏造“最近一次事故”。区分已发生的事实与待验证的机会。

## 从业务方案到模块和用户故事

先用业务机制说明如何解决问题，例如“按完好状况和时段占用自动决定能否批准，并记录实际交付与归还”；不能用“做申请模块”代替方案。

按稳定的业务职责归拢能力，说明模块负责什么、输入什么业务事实、向谁交接什么结果。模块可映射候选领域边界，但不是限界上下文的既定划分，更不推导技术服务。

再从角色任务展开用户故事：用简短标题方便定位，完整描述包含角色、具体业务场景、期望行为与业务价值；优先按“作为某角色，在某场景下，我希望完成某任务，以便达成某价值”表达，允许自然语言调整。另用规则与验收说明如何判断完成，不把所有细节挤进标题或一句故事里。

例如标题“申请人撤销未领取的借用”，描述“作为借用申请人，在申请已批准且尚未领取器材、也不再需要本次借用时，我希望撤销申请，以便释放不再需要的器材时段”。资格、完成标准和失败去向由业务确认，不能照抄例子。

用“业务目标/痛点 → 方案 → 模块能力 → 用户故事 → 规则与验收”核对追溯：核心模块不能只有名称没有故事，核心故事不能只有操作没有价值，关键规则不能散落而找不到适用故事。支撑能力可以关联所服务的故事，不虚构“系统用户”来凑故事。

## 业务语言：同一个词是否真的同义

出现“一词多义、同物异名、状态含糊”时，先对齐它在具体场景中的含义。

- “可用”是设备完好，还是在指定时段尚未被占用？
- “完成”是申请批准、物品交付，还是使用后归还？
- 两个编号相同的东西是否代表同一个业务对象？改变属性后，业务上还是原来的那个对象吗？

需要区分时，用“可借时段”“设备完好”等明确业务称谓。仅记录影响规则的术语，不自动生成术语大全、实体表或类设计。

## 行为、事件与生命周期

围绕“谁想做什么”和“业务上已经发生什么”核对：

```text
参与者提出动作 → 检查前提与责任 → 接受或拒绝 → 产生业务结果 → 下一位参与者继续处理
```

问清动作作用的对象、允许条件、拒绝后去向和结束标准。“申请撤销”是意图，“申请已撤销”是完成事实；提交成功不能直接等于审批通过，点击按钮不能直接等于业务完成。

只有流转会改变规则时才展开状态。用已批准、已交付等业务状态表达，不设计状态码。业务事件用于理解结果与交接，不推导消息队列或事件溯源。

## 始终成立的规则与一致性要求

出现占用、额度、数量、互斥操作、多人处理等信号时，寻找业务不变量：无论谁操作、重复几次或先后顺序如何，都不能破坏什么规则？

- 同一设备在重叠时段能否承诺给两个申请？
- 撤销与交付同时发生，哪种结果允许成立？
- 同一请求重复提交，是同一次业务动作还是新申请？
- 一个结果依赖两方完成时，何时能向用户宣告成功？一方失败后谁处理？

先确认可接受的业务结果和恢复责任。不指定锁、事务、聚合根、补偿代码或一致性技术方案。小工具的规则可聚焦输入合法性、结果正确性和失败处理，仍需关联其业务目标与用户故事。

## 职责与含义的边界

出现多个业务责任方、不同术语含义或不同规则时，探查各自负责的决定与事实：谁可以改变规则，谁是结果的权威来源，交接给另一方的是什么？

例如资产管理确认设备是否完好，借用管理决定某时段能否借出。两者都说“可用”，含义可能不同，需要明确交接条件。

这能帮助发现限界上下文的候选边界，但不要根据菜单、部门、代码目录或角色数直接宣布上下文划分。没有足够业务证据时，记录已知职责和未决边界即可。业务边界不自动等于微服务边界。

## 规则边界案例与业务验收

对重要规则优先选一个能区分不同解释的例子：允许、拒绝、临界条件、重复或冲突。例如“已批准但尚未交付的申请，申请人可撤销；已交付后走归还流程”。

用参与者、前提、动作和可观察结果确认理解，不要求用户写 Given/When/Then。目标和验收要对应；“有撤销按钮”只能证明入口存在，不能证明撤销和占用释放完成。

若“提高效率”等目标没有测量依据，询问可观察变化或验证方法；未知数值标为待验证，不编造提升比例。

## 只沿有信号的风险继续问

涉及身份或敏感信息才展开数据归属与可见范围；涉及外部交接才展开依赖失败；涉及历史记录或在途事项才讨论旧规则；涉及时效、追责或争议才讨论相应约束。

把问题压缩成可裁决的业务选择，说明不同答案如何改变范围。用户不能回答时，明确需要谁提供什么证据或决定，停止重复追问该缺口。

## 概念依据

本 Skill 将下述 DDD 概念用于业务澄清；提问顺序、材料要求和基线交付方式是本 Skill 的工作约定。普通使用无需逐次访问这些链接。

- [Eric Evans：DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)：业务模型、通用语言、业务事件与一致性边界的概念依据。
- [Martin Fowler：Ubiquitous Language](https://martinfowler.com/bliki/UbiquitousLanguage.html)：领域专家与开发者共同使用、随理解更新的业务语言。
- [Martin Fowler：Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)：模型适用的明确边界，以及边界间的关系。
