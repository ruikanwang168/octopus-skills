# 业务需求基线输出参考

本文件只在核心业务共识已经确认、用户要求生成或更新正式文档时读取。它提供输出选择和内容校验，不是固定模板；不得为了套用示例而补造结论。

## 生成前门槛

满足以下条件才生成正式基线：

1. 已确认本次是全新产品、增量迭代或小工具，且路由依据清楚。
2. 真实问题、目标结果和最小必要能力已经过因果与反事实检查。
3. 本期范围、范围外、保持不变和后续项有判断依据。
4. 主流程能从触发走到业务结果，关键失败有业务去向。
5. 核心角色、责任交接、现状与目标差异已经明确，或具体标记为待确认。
6. 用户已经确认核心共识；非阻塞待确认项已说明影响并得到接受。

目标、范围、主流程、核心责任或增量兼容策略存在阻塞性冲突时，返回澄清阶段，不把推测写成事实。

## 最终校验闸门

生成前必须执行一次完整内容校验和语义冲突扫描。只要有一项必过项不通过，就不能落盘：

1. 标出失败项及其影响；
2. 回到对话澄清、修正假设或重新划分范围；
3. 更新确认摘要；
4. 重新校验，直到全部必过项通过。

如果缺少外部材料或其他业务方决策，明确记录阻塞对象、所需信息和不补充的影响；暂停等待不等于校验通过。非阻塞待确认项只有在用户知情接受其影响后，才可以作为“带待确认项”基线的一部分通过校验。

## 选择输出形式

输出形式不固定，应根据项目和材料选择最清楚的形式，不要求所有项目使用同一种结构：

- 短文：适合场景单一、结论少的小需求；
- 结论清单：适合用户已给出大量事实，需要快速确认判断；
- 表格：适合角色、范围、变化、风险或多项决策的并列比较；
- 流程图：适合交接多、状态变化多或异常分支影响大的流程；
- 组合：用短文讲核心判断，用局部表格或流程图承载复杂关系。

可以使用任意清晰的标题。不要为了“覆盖 16 点”强行创建章节，也不要把四层分类写成正式文档结构。

## 最小内容契约

无论采用何种版式，读者都应能从文档中找到以下结论；不适用项可以省略并说明理由：

### 问题与结果

- 业务场景和改变原因；
- 当前做法和真正障碍；
- 影响对象和业务后果；
- 期望结果及其观察或验证方式。

### 方案与必要性

- 用什么业务机制或能力解决问题；
- 为什么这些能力必要；
- 不做其中某项时会发生什么，是否有更小或现有能力的替代方案；
- 谁的责任、动作或交接发生变化。

### 范围与边界

- 本期必须改变的内容及依据；
- 明确不处理的内容及排除理由；
- 保持不变的规则、责任、数据或流程；
- 后续扩展及其前提；
- 可能触发重新评估的假设。

### 流程与防御

- 主流程从触发到结果的关键节点；
- 关键异常、重复、撤回、失败、重试、回滚、补偿或转人工；
- 适用的外部依赖、历史兼容、业务量级和审计要求；
- 依赖不可用、历史数据不兼容或业务量超过预期时的处理原则。

### 不确定性

- 已确认事实和决策；
- 当前推测及依据；
- 待确认问题、回答者或来源；
- 每个待确认项不确认的具体影响。

## 可选结构示例

以下只是可选形状，不是必须复制的模板。

### 小工具

```md
# 需求基线：<名称>

## 核心判断
<场景、痛点、结果和边界>

## 处理链路
输入 → 处理 → 输出

## 必要动作与异常
| 动作 | 必要性依据 | 处理结果 | 失败去向 |
|---|---|---|---|

## 待确认
<问题与影响>
```

### 增量迭代

```md
# 需求基线：<名称>

## 本次变化
<现状、变化原因、目标差异>

## 范围判断
<本期、排除、保持不变、后续>

## 业务变化
| 角色/场景 | 原做法 | 本次变化 | 目标结果 | 兼容影响 |
|---|---|---|---|---|

## 风险与待确认
<历史、在途、上下游、失败和未决问题>
```

### 全新产品

```md
# 需求基线：<名称>

## 业务判断
<背景、真实痛点、目标结果>

## 角色与主流程
<关键参与者、交接和主干流程>

## 必要能力与范围
<能力、必要性、包含/不包含/保持不变>

## 业务约束与防御
<对象、状态、数据边界、异常、依赖、量级或审计>
```

如果这些示例不适合当前项目，应换成更清楚的形式，而不是勉强填空。

## 内容校验

落盘前逐项复核：

- 每个核心结论都有用户话语、材料、实际案例或明确决策作为依据；
- 事实、观点、推测、待确认没有混写；
- 问题不是功能名称的同义改写；
- 每项能力或功能都能关联问题、目标、流程节点或风险；
- 关键功能有反事实检验或替代方案判断；
- 范围边界有理由，不以页面数量、字段数量或模块名称定义范围；
- 现状、目标、方案和结果之间没有跳步或矛盾；
- 关键失败不会导致业务对象无人负责或无法恢复；
- 没有凭常识补角色、规模、外部依赖、历史规则或技术约束；
- 没有把业务定义写成数据库、接口、鉴权、状态码、日志或技术架构；
- 输出没有同义重复、空泛评价或为了完整率保留的无关段落；
- 待确认问题具体可回答，并写明不确认的业务影响。
- 关键结论旁有简短判断依据或来源类型；不使用“经过分析”“综合判断”等空话代替依据。
- 已检查知识导航/工作台、静态展示/自动推荐、配置完整度/用户成功、固定范围/可扩展、使用者/维护者等语义冲突。

## 追溯方式

可以使用 `P1`、`C1`、`E1` 等编号，也可以使用自然语言链接或局部表格。编号不是必需格式，但追溯关系必须可读：

```text
业务问题/目标 → 必要能力 → 业务动作或功能 → 预期结果
```

没有直接痛点的能力，必须说明它服务的目标、流程节点或防御风险；不得为了满足编号规则虚构痛点。

## 面向用户的确认摘要

正式文档前的确认摘要不需要复述全部分析过程，只需让用户能够校正关键判断。可以采用任意清晰的形式，但至少说明：

- 当前认为真实问题是什么；
- 这个判断依据了哪些事实、材料或用户说法；
- 哪些仍是推测；
- 哪些冲突会改变产品定位、范围或主流程；
- 下一步需要用户确认的最少问题及其影响。

不要展示冗长的内部思维过程；把思考过程压缩成可核对的依据、影响和决策点。

## 写作约束

- 第一段直接给核心判断，不铺垫行业背景。
- 一句话尽量只表达一个事实、规则或决定。
- 同一事实只在最合适的位置完整表达一次，其他地方引用或简写。
- 明确优先于篇幅，不设最低字数、固定章节数或表格数量。
- 禁止使用“全面提升”“有效赋能”“形成闭环”“综上所述”等套话替代证据。
- 不编造指标；用户不知道技术数字时记录业务频率、高峰和可接受等待时间，或标记待测算。
- 同名 `需求梳理文档.md` 默认更新原文件；用户明确要保留旧版时才新建版本。

## 文档头部建议

可以用简表标记项目类型、文档状态和确认基线，但不是必需格式：

```md
| 项目类型 | 文档状态 | 确认基线 |
|---|---|---|
| 增量迭代 | 已确认 / 带待确认项 | 本次确认 |
```

用户没有提供日期或版本时，只写“本次确认”，不要编造时间。
