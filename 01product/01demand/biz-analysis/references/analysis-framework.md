# 业务分析风险扫描池

本文件在项目类型确认后读取。它提供 16 个可选的风险维度，不是固定目录、问卷或输出模板。只有当用户材料、目标、流程或风险出现相关信号时，才使用对应维度提问和记录。

## 使用方式

1. 先提取用户已经明确说出的事实、判断、目标和变化，不重复询问。
2. 先判断现有系统/流程是否存在，再选择全新产品、增量迭代或小工具路由。
3. 以“这个问题的答案会不会改变业务决策”为准入条件选问题，不按维度顺序推进。
4. 每轮选择 2 到 4 个最能降低重大不确定性的问题，并说明它们影响什么。
5. 每轮回答后更新事实、假设、冲突、范围和风险摘要；只在必要时继续追问。
6. 业务判断已闭环后停止扫描，未触发的维度标记为不适用，不为了完整率补问。

最终校验不通过时不能直接交付：回到未决判断，补充事实或请用户裁决，更新摘要后重新扫描。只有全部必过项通过，或非阻塞待确认项已被用户知情接受，才算通过；缺少外部材料时明确阻塞，不把阻塞改写成推测。

## 适用性矩阵

| 风险维度 | 全新产品 | 增量迭代 | 小工具 | 触发信号 |
|---|---|---|---|---|
| 名词与口径 | 按需 | 仅新增或变化的领域词 | 通常省略 | 术语差异会改变范围、规则或结果 |
| 业务背景 | 必须 | 只写本次变化背景 | 简写 | 不清楚为什么现在要改变 |
| 真实痛点 | 必须 | 必须 | 必须 | 用户只描述功能、页面或方案 |
| 涉及角色 | 主流程涉及者 | 受本次变化影响者 | 通常省略 | 责任、交接或受益/受损对象不清 |
| 解决机制 | 必须 | 必须 | 必须 | 还没有从问题推导出必要能力 |
| 实现边界 | 必须 | 必须 | 必须 | 需求可能扩张，或包含/排除没有依据 |
| 核心流程 | 全景主干 | 现状到目标的变化 | 输入→处理→输出 | 关键节点、交接或结果不闭环 |
| 功能/动作 | 按角色和场景 | 仅新增、修改、废弃 | 极简动作点 | 需要转成后续任务或验证必要性 |
| 业务实体 | 核心对象 | 本次新增/修改对象 | 通常省略 | 对象身份、关系或生命周期有歧义 |
| 业务状态 | 关键对象状态 | 受影响状态变化 | 通常省略 | 事件、流转条件或非法流转不清 |
| 数据边界 | 业务级可见/操作范围 | 本次变化 | 通常省略 | 越权、归属或敏感信息风险 |
| 异常兜底 | 关键失败路径 | 本次变化带来的失败 | 必须 | 中断、重复、无结果或无人负责 |
| 外部依赖 | 主流程约束 | 新增/变化依赖 | 有依赖才分析 | 依赖不可用会改变业务结果 |
| 历史兼容 | 无历史则不适用 | 必须判断 | 通常省略 | 历史数据、在途业务、报表或通知受影响 |
| 业务量与时效 | 有规模信号才深入 | 有规模或时效变化才深入 | 通常省略 | 高峰、频率、容量或等待时间会改变方案 |
| 审计与发现 | 有责任/合规/争议信号才深入 | 本次相关事件 | 通常省略 | 需要追责、统计、告警或异常发现 |

“必须”表示必须形成业务结论，不表示必须使用固定章节。条件维度没有信号时直接记录“不适用”或“不受影响”。高风险、合规、迁移或规模要求可以把条件维度提升为必查，并向用户说明原因。

## 覆盖状态

只对已经触发的维度记录状态：

| 状态 | 含义 | 处理方式 |
|---|---|---|
| 已确认 | 用户明确提供或确认，且没有未处理冲突 | 直接使用，不重复问 |
| 当前推测 | 有合理依据但尚未确认 | 在摘要中标注依据和需要确认的点 |
| 待确认 | 缺失、冲突或需要业务决策 | 具体提问，注明影响 |
| 不适用 | 当前项目没有适用信号 | 不继续深挖 |

“当前推测”不能改写成事实。多份材料或多次口述冲突时，说明各自来源、冲突内容以及对目标、范围、流程或风险的影响，请用户裁决。

## 证据与判断

区分以下信息类型：

- 事实：用户明确说明、现行系统/流程材料明确展示或可直接观察的情况。
- 用户观点：用户对原因、优先级或方案的判断，不能直接当作事实。
- 推测：基于上下文提出的临时假设，必须标注依据。
- 决策：用户确认采用的目标、范围、规则、责任或处理原则。

未来如何运行以业务方当前明确决定为准；当前如何运行优先依据现行系统、流程材料和实际操作说明；截图和原型只证明画面中明确展示的内容，不证明隐藏规则或完整流程。不能通过互联网搜索补造企业内部规则、系统现状或实际流程。

## 深挖判断

对用户提出的功能、页面或方案，至少完成一次以下检查；如果答案已经明确，不必重复追问：

1. 场景：谁在什么情况下遇到问题，频率或影响是否具体？
2. 当前做法：现在如何完成任务，哪个节点真正卡住？
3. 根因：问题是能力、规则、责任、数据还是执行成本？
4. 结果：希望改变什么可观察的业务结果、规则或责任关系？
5. 反事实：不做该功能能否用现有能力或更小变化达成目标？
6. 代价：谁新增工作、等待、审核、维护、学习或出错成本？
7. 替代与边界：哪些是必要能力，哪些是便利项、偏好或后续扩展？

停止条件是：根因、业务影响、期望结果、必要能力和最小边界已明确；或用户需要查材料/协调他人；或剩余问题只影响页面、文案或技术实现。

“停止深挖”不等于“允许交付”。停止深挖后仍要执行最终校验；如果校验发现核心结论冲突或缺少依据，必须重新进入澄清循环。

## 用户引导式提问

提问不是让用户完成分析表，而是帮助用户把模糊想法变成可判断的业务事实。每轮问题前先给出一句当前判断和它的依据，再说明问题会影响哪个决策。

优先使用以下方式降低回答门槛：

- 具体案例：请用户描述最近一次发生的任务、参与者、当前做法和结果；
- 对比选择：把两种可能的目标、责任或范围并列，请用户选择或修正；
- 反事实：如果不做该功能，用户会继续怎样完成，哪种后果不可接受；
- 取舍排序：本期只能保留一项时，哪一项直接决定核心结果；
- 影响追问：如果采用/不采用某方案，谁会新增工作、等待、风险或责任；
- 证据追问：这是亲历事实、材料结论、个人判断，还是暂时猜测。

用户回答后先复述“已确认什么、仍假设什么、这会改变什么”，再决定是否继续。不要为了覆盖维度而把问题改写成抽象术语，也不要让用户猜 QPS、字段或技术实现。

分析过程可以有明确的思路顺序，但对用户只展示简短判断依据、影响和待决策点，不输出冗长的内部思维过程。

## 范围论证

范围结论必须带依据：

- 纳入项：哪个目标、痛点、流程节点或风险证明它本期必要；
- 排除项：为什么不影响核心结果，或属于职责外、数据外、能力外范围；
- 保持不变：哪些现有规则、责任、数据或流程不能被本次需求误改；
- 后续项：依赖什么前提、数据或业务决策才能进入后续版本；
- 重新评估条件：哪个假设失败会迫使范围、方案或路由改变。

增量需求必须额外核对历史数据、在途业务、报表统计、通知、权限、上下游兼容和失败处理。没有影响时形成“不受影响”的明确结论。

## 常见语义冲突

以下冲突一旦出现，优先澄清定位，不要直接写成两个都成立的结论：

| 冲突 | 需要澄清的业务差异 |
|---|---|
| 知识导航 vs 工作台 | 是否保存进度、判断下一步、记录完成状态或支持返工 |
| 静态展示 vs 自动推荐/执行 | 系统只提供信息，还是需要输入、规则判断和自动动作 |
| 配置完整度 vs 用户成功 | 节点/链接齐全，是否等于用户能完成任务 |
| 固定范围 vs 可扩展配置 | 第一期支持固定类型，还是后台可以新增类型、节点或路径 |
| 使用者 vs 内容维护者 | 谁消费内容、谁发布修改、谁对错误负责 |
| 删除能力 vs 无恢复机制 | 误删、错误发布和链接失效是否可接受，最低恢复原则是什么 |
| 最小能力 vs 便利项 | 不做该项是否仍能完成核心结果，是否有人工或现有能力替代 |

记录冲突时，至少说明冲突双方、各自影响、当前临时解释和需要用户裁决的问题。

## 风险维度的业务边界

只记录业务定义，不进入技术实现：

- 名词与口径：只收录会改变范围、规则或结果的核心领域词。
- 角色：记录谁执行动作、谁接收交接、谁对结果负责；不能按常见系统角色补齐。
- 实体：只有具备独立业务身份和相对独立生命周期的对象才单列；属性、明细、附件、规则和页面区块并入上级对象。
- 状态：记录业务对象、触发事件、流转条件、非法流转和异常去向；不写状态码或技术状态机。
- 数据边界：使用组织、归属、业务属性和敏感信息表达可见/可操作范围；不设计鉴权配置。
- 非功能：优先记录用户量、业务频率、高峰和可接受等待时间；不编造 QPS，也不设计缓存或架构。
- 审计：记录需要追责、统计、争议处理或异常发现的业务事件；不写日志格式、埋点代码或监控实现。

## 项目类型停止标准

### 全新产品

- 没有现有系统/流程的隐含依赖，或用户明确接受全量重建的兼容范围；
- 真实痛点、角色责任、主流程、最小能力和本期边界已确认；
- 关键异常和必要的外部依赖有业务去向；
- 条件维度已判断适用、不适用或待判断，未确认项的影响已暴露。

### 增量迭代

- 现状、变化节点和目标差异明确；
- 新增、修改、废弃能力都能说明必要性和受影响角色；
- 历史数据、在途业务、报表、通知、权限、上下游和失败处理已经形成结论或具体待确认项；
- 没有把未变化的全量系统重新梳理成模板文档。

### 小工具

- 痛点、输入、处理、输出、最小边界和关键异常已经闭环；
- 动作点没有扩张成产品模块；
- 没有适用信号时，不主动深挖角色、实体、状态、权限、历史、规模和审计。
